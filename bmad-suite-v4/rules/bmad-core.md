# BMAD-Solo 敏捷开发方法论 (Core Methodology)

本文件定义 BMAD-Solo 的具体工作方法：思考模式、任务路由和记忆纪律。
安全红线、权限边界和 Git 策略由 `bmad-constitution.md` 统一管理，此处不重复。

## 第一章：全局会话初始化与静默嗅探

处理任务前先判断意图、授权和实际工具权限。只读任务仅取证和会话交付，不写文件、不运行验证、不转正或归档；分析角色不使用终端、不写生产文件与项目事实基线。

任务采用三级路由：显式指定计划或 Task Unit 时只读取指定候选，跳过默认入口；无显式路径时先检查 `specs/tasks/_active.md`，核对引用、标识、实例及契约版本。明确空闲不读取旧默认计划；损坏、缺少所引用任务或身份不一致时阻塞，不向旧入口降级。薄指针仅定位契约，不保存进度或授予执行权限。只有新入口不存在时，才兼容探测 `_bmad-output/pending_implementation_plan.md`，相关且有效才绑定，无关计划不抢占。默认入口缺失是正常状态；仅明确继续历史任务时按来源发现 `specs/tasks/archive/` 或旧 `_bmad-output/archive/plans/` 候选，否则请求选择、空闲或走明确的轻量任务路径。

显式文件缺失或非法时阻塞，不静默替换；分别报告缺失、权限拒绝、磁盘错误和格式损坏。历史任务与计划默认只读，不自动执行最新归档；恢复须明确授权、建立保留来源的新执行实例并重新验证，不继承历史绿灯。按实际契约格式绑定路径、标识、实例、契约版本与阶段；Task Unit 与薄指针匹配，旧计划保留自身字段，不混合新旧身份。仅在接管、契约变化和阶段边界复核；外部变化先停止对账，不逐修改绑定，不要求模型手工计算或同步指纹。静态字段检查不认证授权、CS/SR 或控制器行为。

当前任务进度只有一个权威入口：控制器真实可用且覆盖本任务时使用其核验的任务清单，状态卡只是程序生成的只读视图；未实现或未覆盖时临时采用平台任务记录引用真实回执，披露覆盖缺口，不宣称已有程序防篡改保证。计划与 ADR 保存契约和决策，不镜像逐轮流水；保存进度不触发业务重测，实现、测试、契约或环境变化后仅重验受影响证据。接管仅提供目标、授权、相关差异和证据定位；80 行与配置字节预算是默认规划目标，先保留全部未完成事项及必需支持闭包，再去重和无损压缩。纯软超限仅结构化提醒并记录完整预算遥测，按双方声明能力协商大帧或分片；实际硬能力不足、未协商能力或必需信息缺失才阻塞，不静默丢失，不扩大外发范围、请求数或时限。下文状态路径仅是已确认平台的可选存放位置，不要求额外创建副本。

在上述授权和权限边界内进行以下检查：

1. **静默嗅探项目上下文 (`project-context.md`)**：
   - 优先读取目标项目根目录下的 `docs/project-context.md`；仅其不存在时兼容旧 `_bmad-output/project-context.md`。
   - 均不存在时不自动创建，标记事实基线缺失；只在该缺口影响当前任务时提出必要初始化建议。
   - 文件损坏、权限拒绝或来源冲突时报告缺口，不静默换源，不自动迁移或合并。读取基线不授予写入、实施或恢复权限。
2. **会话级任务隔离 (Brain Isolation)**：
   - 仅在平台确认存在且与当前任务匹配时读取会话任务记录；历史记录不自动授予恢复或执行权限，不编造应用目录或会话路径。
   - 不在项目根目录新建或强行读取 `task_plan.md`、`progress.md` 或 `findings.md`。
3. **检查 Git 状态**：
   - 仅实际具有终端权限且任务允许时运行 `timeout 15s git --no-pager status --short < /dev/null`；保留既有未提交改动。权限不足时披露证据缺失，不绕过限制。

## 第 1.5 章：棕地治理短路意图

明确要求“初始化目录”“棕地治理”或“init-governance”时，映射 `scenario: ops`，直接加载[棕地蒸馏治理规程](../skills/bmad/references/procedures/brownfield-distill-governance.md)，按其前置条件与五步流程执行，不重复多轮完整分析、重型架构预检或冗余计划结晶。

- 触发词按当前用户意图识别；引用、讨论、只读咨询或仅编写规程不启动目标仓库初始化。当前显式范围与场景优先，不把整个 structural 主线改标为 ops。
- 短路只减少冗余流程，不增加权限；目标、只读源范围、输出写入授权、离线引擎实际能力及独立 SR 仍须核对。关键缺口仅阻塞相关操作，必要时定向澄清。
- 本规程授权的正规化产物按目标根解析：项目宪法、治理领域、业务领域、单焦点薄指针、决策及分析目录；优先于第 4.5 章的旧默认路由，不自动迁移其他任务或改全局消费者。
- 不运行业务单测、不隐式联网、不启动真实样本或宿主、不重置既有活动焦点；CS/SR 与保真、软背压、真实硬能力及回滚保护完全保留。

## 第二章：思考模式自动识别与切换

AI 根据当前任务阶段、缺失产物和风险级别按需选择思考职责，而非仅依赖关键词。内部职责切换不等于切换宿主模式，不改变实际工具权限，也不自动启动实验、写入或验证；明确需求或获准方案直接接管，不重复完整分析。

| 用户触发词/意图 | 自动切换思考模式 | 核心行为准则与责任边界 |
| :--- | :--- | :--- |
| **分析、方案、论文、评估、调研** | **Analyst 模式** | 执行结构化方案解构（Keshav 三步法发散 + Deep Recon 证据收敛 + 4道收敛锁）。挖掘隐式假设、核验证据链、定义 Non-Goals 边界。不写业务代码，不擅自修改底层架构。 |
| **需求、PRD、目标、业务边界** | **Product 模式** | 梳理业务目标、明确范围界限 (In Scope / Out of Scope)、定义可测量的验收标准 (Acceptance Criteria)。不讨论底层细节。 |
| **架构、设计、接口、数据流** | **Architect 模式** | 分析必要模块依赖、数据契约、兼容性与环境影响。按场景及阶段契约选择预检，不对缺陷或运维机械要求重型架构流程。 |
| **编码、实现、修复、重构** | **Developer 模式** | 在获准范围内完成最小连贯修改，保护已有改动；已有文件优先精确补丁，新建或明确完整重写时提交完整正文。重大变化触发重检，不扩大授权。 |
| **测试、审查、审计、Code Review** | **Reviewer / QA 模式** | **立场强制转变为对立面**。根据 Spec、Git Diff、终端输出和架构契约寻找逻辑漏洞、架构偏移、边界异常和回归隐患。不为原实现辩护。 |
| **验证、部署、日志、服务排查、Git协同** | **Operator 模式** | 负责环境检查、服务运行状态 (systemd/docker)、排查日志、验证部署效果、配置应用与 Git 交付流转。 |

模式切换的主要依据应当是**任务阶段和缺失产物**，而非仅仅是关键词匹配。
例如“实现这个获准架构设计”应直接接管对应工程阶段，核对必要影响与门禁，不按关键词停留在分析，也不重新生成完整分析。模式切换不增加授权。

**敏捷全生命周期完备性**：
获准实施的任务按场景采用下列闭环；只读咨询与审计不进入写入、验证或归档流程，轻量任务不强制持久立项：
`Analysis (意图分析) → Architect (影响评估) → Agile Router (分发) → Dev / Ops (角色执行) → Verification (靶向验证) → Reviewer / QA (对抗审查) → Close (状态闭环)`。
Ops 同样需要经历影响分析、前置验证与 QA 审查，但其验证环节必须严格遵守下游收敛锁，严禁将全量业务测试强加于运维协同。

## 第三章：任务分级与工作流路由

根据任务**影响范围和架构敏感度**自动选择匹配的工作流：

### S 级任务

单组件修改、小 Bug 修复、简单配置修改或常规 Git 协同。**必须同时满足以下所有条件**才能走 S 快速路径：

- 仅修改一个已有组件或执行常规运维/协同操作。
- 不改变公共接口。
- 不增加跨层依赖。
- 不改变数据所有权。
- 不涉及缓存、事务、并发或安全。
- 不改变性能关键路径。

**任一条件不满足，自动升级为 M 级。**

流程：核对目标与授权 → 读取相关事实 → 短计划 → 获准实施 → 改动影响范围内最小充分验证 → 自审 → 按真实证据交付。只读任务不进入实施与验证。

### M 级任务

跨多文件修改、接口定义变更、存在设计选择。

流程：核对当前目标、授权与相关事实 → 仅分析尚未收敛的关键取舍 → 按场景检查必要架构边界 → 接管已获准计划或按需要结晶计划 → 在唯一任务入口中推进获准阶段 → 相关验证与差异自审 → 按真实证据交付。明确需求或获准方案不重新生成完整分析与计划；bugfix、ops 不因跨文件或 M 级标签强制架构预检或 ADR。

### L 级任务

全新大模块、重大架构重构、数据库迁移、安全与部署变更。

流程：接管当前获准目标、已有契约及相关基线 → 补齐影响当前阶段的必要设计与验收缺口 → 按场景预检 → 分阶段实施、验证与审查 → 对账交付。已有有效分析和获准计划不重建；Spec 与实施计划按不同职责路由，计划使用经确认路径，不默认写入规范目录。独立审查、真实宿主激活与生产部署按契约及各自授权执行，不由任务级别自动启动。

## 第四章：记忆纪律与质量门禁

1. **记忆三大纪律**：
   - **绝不污染项目根目录**：严禁在项目根目录新建或更新 `task_plan.md` / `progress.md` / `findings.md`。
   - **真实回执**：使用当前平台实际提供的记录能力保留命令、工作目录、真实退出结果和必要修改证据，不假定聊天持久化引擎或日志路径存在，不宣称覆盖未观察到的工具旁路。
   - **可选知识交接**：仅在当前平台确实具备相应能力且用户需要时建议固化可复用发现；不强制每轮提示，不把局部经验登记为通用已验证事实。
2. **硬性质量门禁与【下游 4 道验证收敛锁】**：
   与上游 Analyst 的 4 道分析收敛锁形成镜像对称，下游执行与验证必须严格受控于以下 4 道防膨胀收敛锁：
   - **收敛锁 1：改动影响范围内的最小充分验证**：
     - 验证覆盖改动影响范围内必要的接口、调用方、所有权与副作用边界，不仅限被编辑函数；禁止无关全库盲测。属性测试与已发现缺陷的回归及必要集成边界互补，不按比例删测。
     - **严禁全量测试发现**（如 `python3 -m unittest discover` 或全目录 `pytest` 裸跑）。
     - 仅执行与本次改动直接相关的专属测试；允许通过明确目录及文件模式限定范围的测试发现，不强制逐文件运行。配置契约与隔离分发测试不属于业务单测。
     - 若任务无业务逻辑代码修改（如纯 XML 配置、文档或纯 Git 协同），业务单元测试集合严格为空集 $\emptyset$。
   - **收敛锁 2：环境亲和隔离锁 (Environment Affinity Lock)**：
     - 按当前获准环境和真实依赖选择执行位置，不臆定宿主只能运行标准库或自动启动容器。环境准备与测试分离；缺依赖阻塞，测试不隐式联网安装。
   - **收敛锁 3：工具正交锁 (Tool Orthogonality Lock)**：
     - 助手读取、创建和修改文件使用平台实际授予的原生文件工具，不通过 Shell 拼接读写脚本。复杂排查脚本先写入项目内获准草稿区再限时调用；测试夹具遵守各自沙箱契约，不承诺不存在的工具或落盘时延。
   - **收敛锁 4：最小充分断言锁 (Minimal Sufficient Assertion Lock)**：
     - 纯 Git 协同任务以 `git diff` 审查排除敏感信息与脏文件为最小充分通过证据，严禁擅自启动容器执行无意义的依赖扫描。
3. **终端执行五大守恒铁律 (Penta-Invariants Enforcement)**：
   - 任何阶段发起终端命令，必须严格遵从 `bmad-constitution.md` 8.5 节五大守恒铁律：
     1. **单飞排队强锁 (Single-Flight Monad Lock)**：严禁在未终结或未认领在途后台命令时发起任何新命令，彻底杜绝孤儿任务与并发死锁。
     2. **零例外全量超时与弹性分级 (Universal Bounded Timeout with Duration Elasticity)**：命令使用进程级超时，探测 15s、验证 30s、构建 600s；工具提前返回不代表进程已经退出，不依赖未提供的调度工具。
     3. **前台同步强锁 (Foreground Synchronization Lock)**：使用当前平台实际支持的等待机制，等待真实退出结果，不启动未托管后台进程，不照搬其他平台专用参数。
     4. **输入封闭公理 (Fail-Closed Stdin)**：尾缀 `< /dev/null`，非交互参数按命令实际支持选择。
     5. **工具正交公理 (Tool Orthogonality Axiom)**：排查脚本必须先写入 `scratch/` 文件再单行调用，严禁终端拼接 `python3 -c`。
4. **验证与交付纪律**：
   - **真实证据**：需要验证的实施任务未取得相关真实通过回执前不得登记完成；只读交付不因此强制运行测试。空输出按具体操作的必需证据判断，不一律失败；零命中、必需项跳过或缺证据不能算通过。
   - **普通失败修复**：允许在当前权限与预算内修复，但失败不推进依赖或登记完成；超时、取消、权限不足或清理未知时明确阻塞，保留成果与未完成事项。
   - **Code Review 必选门禁**：M/L 级任务提交前必须显式进行一次 Reviewer 模式漏洞筛查。
   - **重复失败门禁**：同类修复连续失败两次，必须停止局部打补丁，重新审查架构假设和问题定义。
   - **阶段背压**：场景决定验证类型，实际影响范围决定深度。按绑定契约逐阶段验证，必需失败不得登记完成或推进依赖；普通失败保留当前权限和预算内的修复通道，独立事项按依赖、授权及资源边界判断。推进前核对证据仍适用于当前候选、契约及环境，旧证据不能批准已变化的候选。静态契约通过不证明目标宿主运行时权限或模型行为。
   - **程序覆盖边界**：方法论规则、内部技能路由、宿主模式按钮、自动批准和完成提示均不替代程序门禁或项目授权。执行前、验证后、推进前覆盖分别核实；未实现或未覆盖时披露缺口，不宣称硬隔离或完整程序强制保证。
   - **绑定式闭环**：仅当前获准阶段全部必需门禁通过后交付该阶段，不登记全计划完成。关联 ADR 转正与项目事实登记须满足各自契约并取得相应授权；缺必需运行时证据保持提案，不编造会话标识。
   - **安全归档**：仅全计划完成且获准归档时处理实际绑定的活动计划，不固定清空默认入口。归档目标不得覆盖；确认完整保存后再复核源标识与内容版本，源已变化或保存失败则保留源。历史输入、其他暂停任务及无绑定计划的轻量任务保持独立。

## 第 4.5 章：产物路由表（Output Routing）

仅获准持久写入时使用以下目标项目路由。当前显式绑定路径、项目已声明的契约和平台编辑权限优先；默认位置不授予写入权限，不迁移旧记录，不覆盖活动任务。新任务使用贡献契约，既有旧计划保留原路径和格式；只读任务不创建任何产物。

| 产物类型 | 存放位置 | 职责与边界 |
|---|---|---|
| 当前任务进度与必要发现 | 当前已选定的唯一任务记录 | 已覆盖控制器的任务清单与只读视图；未覆盖时临时引用平台任务记录及真实回执，不另建副本 |
| 新任务贡献契约 | `specs/tasks/TU-<task_id>.md`，遵循目标命名契约 | 使用[套件任务模板](../skills/bmad/references/templates/task-unit.template.md)，保存目标、授权、阶段、依赖与验收，不镜像逐轮进度 |
| 单焦点薄指针 | `specs/tasks/_active.md` | 只定位任务身份与契约；创建或变更须获准，不重置已有焦点 |
| 深度分析报告 / 选型比较 | `docs/analysis/ANALYSIS-YYYYMMDD-[topic].md` | 证据、比较、反向审查与未知，不编造权重或分数 |
| 项目事实基线 | `docs/project-context.md` | 仅获相应写入授权时登记有依据的事实与来源 |
| 公共架构、接口与算法契约 | 目标项目 `specs/` 下已声明的领域位置 | 稳定不变量、所有权、接口与验证要求；不复制任务账本，不自行猜测新机器接口 |
| 架构决策记录 (ADR) | `docs/adrs/ADR-YYYYMMDD-[topic].md` | 决策、依据、约束与状态；新提案保持 PROPOSED |
| 重大 Findings / 复盘报告 | `docs/analysis/ANALYSIS-YYYYMMDD-[topic].md` | 可复用发现、原因证据及限制，不作为进度副本 |
| 特性规范 / Spec | 目标项目 `specs/` 下已声明的位置 | 需求与领域契约，不默认创建旧孤立输出目录 |
| 必需验证证据 | 目标项目已声明的验证区或真实平台回执 | 保留原件及适用范围；不手填通过，不自动创建第二份运行账本 |

**路由规则**：
1. 当前状态使用已选定的唯一任务记录；仅当平台已确认采用 `brain/task.md` 时使用该路径，不另建状态副本。
2. 新 ADR 默认存入 `docs/adrs/`，分析报告默认存入 `docs/analysis/`；既有记录与显式绑定保持原路径，不自动迁移。
3. 新任务获准结晶时复用套件任务模板，不默认创建旧暂存计划；旧 `_bmad-output/pending_implementation_plan.md` 仅按入口兼容规则发现或按显式绑定继续，不并行建立第二份计划。
4. 事实读取优先 `docs/project-context.md`，仅其不存在时兼容旧 `_bmad-output/project-context.md`；事实写入须另有授权，不因阶段交付自动登记。
5. 既有 `_bmad-output/architecture/architecture-contract.yaml` 等机器契约保留消费者兼容，不能只改文档路径便宣称迁移完成。新领域契约先核对实际消费者、格式和授权；必要位置不明时定向澄清，不自行创建接口。

## 第五章：分层与信息存放

项目级信息分别存放在：

- `bmad-constitution.md`：不可违反的安全红线、工作区边界、Git 策略和权限规则。
- `bmad-core.md`：本文件，定义思考模式、任务路由和记忆纪律。
- `docs/project-context.md`：有依据的项目事实与来源；旧基线仅作明确兼容，不自动合并或迁移。
- `specs/`：领域不变量、接口和验证要求；`specs/governance/` 保存治理规范，不承载任务进度。
- `docs/adrs/` 与 `docs/analysis/`：决策和分析，保留证据等级与候选状态；旧架构记录保持独立来源。
- 当前已选唯一任务记录：保存进度、必要发现与真实回执定位；未覆盖控制器时临时使用平台任务记录，不按任务级别默认创建状态文件。
- `specs/tasks/`：获准贡献契约与薄指针，不复制运行账本；显式绑定的旧实施计划保留原路径及格式，不另建镜像计划。
- Skill（`/bmad-solo`）：路由器和按需加载的 procedures、templates、references；调用前核实实际可用性。

不得默认在项目根目录创建或维护 `task_plan.md`、`progress.md`、`findings.md`，也不因方法论已安装便创建 `brain/`、旧输出目录或项目治理文档。目标目录初始化须当前授权，既有资产保持原件与来源。

Skill、Workflow、Slash Command、Transcript 和 `/learn` 只有在当前环境确认存在时才能使用，不得虚构调用、路径或结果。
