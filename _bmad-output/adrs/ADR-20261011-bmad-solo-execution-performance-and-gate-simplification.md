# BMAD-Solo 执行性能与门禁去官僚化优化方案

建议把执行治理从“模型反复证明自己遵守流程”，改为“阶段级契约绑定、语义批次验证、有界状态投影和可复用的受控执行入口”。保留授权、资产保护和真实验收，删除与业务正确性无直接关系的微步哈希、重复总账和文档自证回环。

- 立即优化规则和验证入口，不以先建设完整控制器平台为前提。
- 日常编码不计算计划、ADR 或执行记录的指纹；阶段入口和出口集中处理。
- 当前状态卡不超过80行；历史不再由模型复制进一个不断增长的 YAML 文档。
- 验证针对行为、接口及必要安全契约，不以测试函数数量或措辞镜像判定正确。
- 允许有界、前台、受监督的复合命令；不允许借合并命令绕过授权或掩盖失败。
- 本文是待评审提案。补丁、状态模板和后续验证用例均未应用，不表示已获实施或部署授权。

## 1. 目标、约束与裁决范围

### 1.1 目标

1. 降低模型用于计划重读、哈希对账、状态重写和成功日志解析的开销。
2. 缩短“明确需求 → 修改 → 相关验证 → 交付”的有效反馈回路。
3. 保留当前任务与历史任务隔离、既有用户改动保护、真实验证和失败不冒充通过等边界。
4. 使自然语言需求成为默认入口，模式和技能名称成为可选快捷方式，而不是正确执行的口令。

### 1.2 非目标

- 不修改生产规则、分发脚本、客户端配置或项目事实基线；本轮仅新增提案文档。
- 不重放历史业务任务，不修改其既有授权、已接受 ADR 或暂停状态。
- 不取消竞态检测、资源测量或必要的集成验收，不用更少测试伪装效率提升。
- 不建设新的多智能体平台，不引入常驻模型调度器或每补丁一次架构评审。
- 不承诺容器能够提供绝对安全、测试能够证明不存在任何竞态，或路由模型永远理解正确。

### 1.3 历史不变量与拟调整边界

已接受的生命周期 ADR 要求显式任务优先、相关计划绑定、历史只读发现、授权恢复及保护第三方受管资产；这些原则全部保留。[13]

本提案只调整开发循环中的绑定频率、状态存储、验证选择和命令监督粒度。受管部署中的提交前指纹复核、备份、所有权和恢复日志属于资产事务保护，不能套用“取消微步哈希”一并删除。[13][14]

既有生命周期 ADR 已明确把特定客户端权限执行委托平台，不把静态配置当成运行时拒绝证据；本提案不重新引入 Agent 自指黑盒测试作为所有任务的前置门。[13]

### 2.2 对用户症状的证据校正

- “1400多行”是用户提供的症状。本轮能定位的执行记录快照为994行；未据此否认后续增长，但不能把1400行写成已独立核验的计数。[11]
- “每次实现有5—8轮 SHA256”作为待测性能假设保留。现有材料确认反复绑定和哈希命令，但没有完成全会话去重统计，不能声称精确测得5—8轮。[11]
- 历史材料报告过11批、42个测试声明匹配；已读业务检查器还要求三份准备资产存在，但尚未取得另一份索引检查器的完整源码，不能认定它必然把“顶层函数数目等于N”设为失败门。[11]
- YAML 别名一律拒绝确实存在于业务项目自建检查器；仓库通用检查器采用安全加载并拒绝重复键，不应把两者混称为同一实现。[10][11]
- 单次日志确实显示14个包的安装动作；“198.1 MiB in 31 packages”不能直接当成每次下载198.1 MiB的证据，也不能据单份日志断定所有调用都重复安装。[12]
- 该日志中包安装输出位于第8—23行，后续大量内容是逐测试 JSON 事件。只静默系统包安装，不能解决完整的上下文膨胀问题。[12]

### 2.3 因果链

综合上述证据，本提案的架构推断是：

1. 宽泛的“每次修改前复核”被扩展为每个编辑动作都需要仪式性绑定。
2. 可变进度被写入计划、ADR 和执行记录，多处镜像导致联动修改。
3. 自建检查器把措辞、资产声明和授权语义一起检查，任何同步遗漏都阻断推进。
4. 为证明同步完成，再保存检查结果；保存又产生“本次更新尚未复验”。
5. 构建、验证和日志审阅分散成多个模型回合，使环境初始化和上下文回灌重复发生。

因此，问题不是“SHA256算法太慢”，而是检查次数、工具往返和文本搬运被放大。该推断不要求放弃哈希、静态检查或容器，而要求给它们正确的生命周期。

## 3. 决策一：阶段级绑定，取消微步指纹仪式

### 3.1 正常执行路径

- 阶段入口：读取相关契约一次，确认任务、授权、版本和验收；集中绑定计划及必要 ADR 指纹，保存一次工作区基线。
- 阶段内：以实际目标文件内容和 Git 状态、差异识别改动；完成一个语义变更批次后做相关验证，不重新哈希计划、ADR、状态卡或每个文件。
- 阶段出口：冻结候选输入，汇总本阶段必需验证；集中核对契约、候选身份和出口证据后推进。
- 对一个未中断、未修订的阶段，正常绑定检查为入口和出口两次；一次批处理可计算多个必要对象，不等于每个对象单独一个模型回合。

“语义变更批次”是能够说明一个行为目的、影响范围及验证选择的一组编辑，不按文件数、补丁工具调用数或代码行数切分。

### 3.2 不以 Git 状态冒充事务锁

Git 状态和差异用于变化观察，不提供写入原子性，也不足以证明文件在检查后未再变化。已暂存与未暂存改动都要考虑；未跟踪文件按目标实际读取，不要求把用户文件加入暂存区。

保护既有改动仍依赖原生精准编辑、预期原文匹配或平台实际支持的版本冲突检测。它们不是每次重新计算计划指纹的理由。没有写入隔离能力时，应明确单写入者前提，不能宣称已经阻止所有外部竞态。

### 3.3 中断与契约变化

以下情况结束当前阶段实例或进入重新接管，再执行新的阶段入口检查：

- 用户调整范围、授权或必需验收。
- 活动契约被替换，出现无法解释的目标文件变化。
- 会话中断导致绑定信息不可恢复，或执行环境身份改变。

它们不是“每改一行就创建新阶段”的豁免口。普通代码或测试编辑不得改变契约修订；已知未变化的契约不重复读取全文。

任务内验证证据可以在绑定输入未变化的条件下使用；历史任务的绿灯不得自动继承。相关源码、测试或环境发生变化后，受影响结果标为过期，不能仅凭上次退出码继续交付。

### 3.4 保留的高风险事务检查

部署、归档源清理、覆盖已有资产等操作仍须保留各自的身份复核和冲突保护。它们是低频资产事务，而不是日常编码微步。[13]

## 4. 决策二：当前状态、契约和证据分离

### 4.1 三类信息各有一个来源

| 信息 | 唯一职责 | 更新时机 |
|---|---|---|
| 计划与 ADR | 目标、授权来源、边界、验收和决策理由 | 获准的契约修订；不记录每次测试或编辑 |
| 当前状态卡 | 当前阶段、候选、最新门禁状态及最近一次验证定位 | 语义批次验证结束、阶段转换、暂停或交接 |
| 工具产物与阶段回执 | 实际命令、退出状态、日志、测试命中及候选身份 | 工具自动生成；模型只消费摘要和必要片段 |

禁止把第三类内容复制成状态卡里的历史数组，也禁止在计划、ADR 和状态卡之间维护逐字段全文镜像。

### 4.2 状态卡规范

建议采用新的状态卡协议，而不是静默改变现有声明与义务模板的含义。示意文件为 [`task-status.yaml`](../analysis/bmad-execution-example/task-status.yaml)，该链接仅表示拟议路径，本轮不创建此文件。

- 最多80个物理行，并建议同时限制为8 KiB；标量建议不超过1024字节。
- 禁止以单行长 JSON、编码文本或折叠块绕过容量限制。
- 不存历史调用标识数组、历史指纹数组、完整测试列表或失败流水。
- 保留任务身份、契约引用、当前阶段和最新验证，避免“只有退出码、不知道属于谁”的假简化。
- 状态卡是投影，不是授权来源，也不是可以凭自身声明授予通过的凭证。
- 多项必需验收必须由当前候选的阶段回执汇总；最后一个命令成功不能覆盖前面失败、跳过或未运行的门禁。

以下是结构示例，所有空值表示尚未知或未运行，不是可执行计划：

```yaml
schema_version: 2
kind: bmad-task-status
task_id: null
plan_ref: null
contract_revision: null
phase: null
state: INTAKE
candidate_ref: null
checkpoint_ref: null
gate:
  scope: null
  status: NOT_RUN
  required_set_ref: null
  evidence_ref: null
  reason: null
last_verification:
  command: null
  cwd: null
  exit_code: null
  result: NOT_RUN
  matched_tests: null
  failed_tests: null
  skipped_tests: null
  started_at: null
  finished_at: null
  artifact_ref: null
  cleanup: UNKNOWN
next_action: null
blocker: null
updated_at: null
```

该示例为30行。实际实例不得为了填满模板编造时间、调用标识、候选版本或测试数量；不适用的测试数量保持空值并由验证类型解释。

### 4.3 消除自证回环

状态保存流程为：取得工具结果 → 构造下一版状态 → 在内存中检查必要类型和容量 → 通过受控写入保存一次。

保存状态不使业务验证失效。状态文件不作为自己通过证明的摘要输入，也不触发“登记这次状态检查，再检查登记结果”的递归。

写入失败时保留旧卡，标记检查点保存失败；已有业务结果仍是已有结果，但不能声称交接状态已可靠保存。根据失败是否影响安全继续或停止，不一律重跑业务测试。

### 4.4 历史如何保留

用户提出由 Git commit 与会话流承载历史，方向正确，但二者不能无条件替代测试证据：

- Git 只保留实际提交的内容；不得为了记账自动提交、推送或暂存用户改动。
- 会话流只有在平台实际保存且可恢复时才可作为历史来源；不能预设某个审计引擎必然存在。[5]
- 原始工具产物保留在获准的任务隔离区；当前卡只引用最新证据。阶段出口保留一个候选验收回执，按任务需求设定容量与保留期，不复制完整历史。
- 迁移旧总账时先保留原件，再提取当前状态和未完成事项；不删除旧任务，也不把未完成门禁改为通过。

状态卡瘦身不是审计证据销毁；无需保存每个模型思考步骤，但要保留支撑当前交付结论的实际证据。

## 5. 决策三：去脆弱元检查，不取消安全契约

### 5.1 删除或降级的检查

- 测试顶层函数数量必须等于一个手工登记常数。
- 为了证明新增测试存在，要求先编写一个解析测试声明的项目专用脚本。
- 要求计划、ADR、状态卡重复写同一授权自然语言，并逐字相等。
- 将文档必须出现某个中文词语作为业务阶段通过条件。
- 状态卡每更新一次，就重跑计划、ADR 和历史证据的全部检查。

这些检查不得作为普通编码批次的强制前置门。若数量本身是业务契约，例如协议枚举基数或资源额度，则仍可测试其真实语义；本条不禁止这种行为断言。

### 5.2 必须保留的检查

- 配置可解析、必要字段类型正确、重复键无歧义、引用没有越界。
- 未知授权不按允许处理；授权引用存在且操作没有超出范围。
- 选定验证资产可运行，并实际命中要求的行为；测试选择为空不是绿灯。
- 失败、超时、跳过、证据缺失及清理失败分别可见。
- 验证范围覆盖改动影响闭包，不仅是字面修改文件；共享接口、依赖方和并发路径按风险加入相关回归。
- 不把配置校验当作运行时证明，不把竞态插桩下的进程内存当作未插桩 RSS 验收。

### 5.3 YAML 别名的处理

不能把“允许别名”本身当成去官僚化目标。对于短小机器生成状态卡，禁用别名可以是合理、低成本的格式限制；对于人工维护配置，如平台需要别名，应使用有资源边界的安全解析并保持重复键语义明确。

本提案要求的是：由共享解析器按输入类型定义一次规则，而不是每个业务任务临时生成不同解析器，再让别名政策成为代码功能验收门。现有通用检查器已经区分了安全加载和重复键拒绝，不应被整体删除。[10]

### 5.4 执行结果摘要

建议验证入口在原始输出进入模型上下文之前生成摘要：

- 成功摘要建议不超过2 KiB：候选、验证范围、命中、失败、跳过、耗时、退出状态和产物引用。
- 失败摘要建议不超过8 KiB：失败阶段、必要错误上下文、定位及产物引用。
- 先解析完整结果，再裁剪展示；不能先截断日志，再依据残片宣称没有失败或竞态告警。
- 超出预算时显式报告截断和未展示内容，保留完整产物；需要时定向读取，不默认重读全量成功日志。

这些是待实现的默认预算，不是本轮已经测得的最佳参数。

## 6. 决策四：单飞是一个监督作业，不是一个简单命令

用户示例中，复合链可以满足单飞前台执行，但管道不是“只有一个进程”：生产者和日志接收者通常同时存在。应把单飞约束定义为同一工作区只有一个未完成的受监督终端作业，而不是禁止该作业内的正常管道或受控子进程。

### 6.1 合规条件

1. 整个作业处于明确的任务授权范围，不把无关修改或部署拼入验证命令。
2. 依赖步骤按成功条件衔接，管道启用失败传播；前一个步骤失败时，后续依赖步骤不执行。
3. 外层包裹整个作业，设置总时限和终止宽限期；不同类别的构建、验证仍有各自的子预算。
4. 标准输入在作业入口封闭，但管道消费者仍读取管道，不能给消费者错误地重定向空输入。
5. 等待整个作业及清理结果；工具提前返回不视为进程结束。
6. 日志路径位于已授权产物区，拒绝覆盖用户文件或跟随不安全链接；日志产生是验证副作用，不是绕过原生工具编辑源码。
7. 不以管道最后一个程序成功代替上游成功；还需保留分阶段结果。
8. 对容器、守护进程或脱离进程组的子进程，使用实际可用的生命周期管理；单独的外层超时不能宣称保证清理所有外部资源。

### 6.2 结构示例

下列 Bash 示例仅说明监督范围与失败传播，未执行。产物路径必须先由受控入口校验并通过环境变量传入；不能把任意模型提供的路径直接视为安全路径。

```bash
timeout --kill-after=5s 30s bash -o pipefail -c '
  : "${ARTIFACT_LOG:?需要预先批准的日志路径}"
  (git --no-pager diff --check && git --no-pager diff --stat) 2>&1 |
    tee -- "$ARTIFACT_LOG"
' < /dev/null
```

对用户原始写法还需澄清：未分组时，日志接收者只接收后一个管道的输出；要记录整个依赖链，应显式分组。即便启用失败传播，也应由执行入口分别记录检查失败、日志写入失败和超时，而不是仅输出一个模糊失败。

不通过批处理延长原来允许的工作范围。批处理减少模型往返，不减少必需验证，也不允许同时启动另一个未受监督的终端作业。

## 8. 延续会话结论：三层验证与自动路由

### 8.1 L0：不可变工具链，不是每次冷启动安装

- 工具链、系统包与离线依赖在独立、获准的准备阶段完成；固定镜像或等效运行器身份。
- 代码改变不重建工具链。只有工具链定义、依赖锁定或安全更新改变时，才重新准备对应环境。
- 测试期间缺依赖即报告环境阻塞，不安装补齐、不临时联网。
- 临时测试现场可以每次新建；复用工具链不等于复用污染的可写运行状态。
- 缓存按工具链、平台、依赖和插桩类型隔离；缓存命中不能冒充本次真实测试执行。

### 8.2 L1：有隔离的快速反馈，不必退回宿主

- 一个语义变更批次形成一次相关验证请求；可连续完成若干编辑，再验证这个完整行为。
- 并发、取消、共享状态或资源所有权变化，局部回环就运行相关竞态或资源断言；不把这些全部拖到交付末尾。
- 无相关并发风险的改动不自动运行全套竞态矩阵。
- 若现有授权要求禁网和源码只读挂载，L1继续遵守；速度来自预置环境、缓存和定向范围，而不是解除隔离。

### 8.3 L2：阶段候选的最终物理验收

- 每个阶段交付候选运行约定的完整必需集合，而不是每次补丁重跑完整集合。
- 独立未插桩进程的 RSS、竞态插桩测试和其他平台矩阵分别记录，不互相替代。
- 出口验收期间冻结候选；输入变化使相关证据过期。只有未变化且有明确绑定的结果才可复用。
- 本地验证通过不自动授予部署、联网、ADR转正或历史归档权限。

### 8.4 自动路由只负责选择行为

目标交互是“直接表达需求”，不是要求用户记忆模式或技能命令。建议常驻一份简短路由契约，深度分析、实现和复核内容按需加载。

- 只读咨询直接回答，不创建计划或状态卡。
- 明确局部修复按当前授权实施，不强制先进入深度分析。
- 复杂设计先收敛方案；关键授权或业务歧义才询问用户。
- 显式模式选择是偏好，不扩大权限；忘记模式名不应让方法论失效。
- Roo 以其实际支持的模式与工具机制适配，Antigravity以实际支持的规则、技能与工具机制适配；本轮未核验目标版本的自动加载、切换或拦截能力，不沿用前序回答中未经本轮证据支持的平台保证。

首版不要求完整控制器接管模型循环。先实现一个可维护的验证入口、短摘要和状态投影；只有所有相关工具请求确实经过检查时，才可称为程序化阻止违规行为。提示词路由和静态路径正则本身不是这个保证。

## 9. 迁移顺序与验收设计

以下为待批准的实施分期，不是活动执行计划，也不触发默认计划写入。

1. 冻结最小契约：评审本提案，确认绑定频率、状态卡、证据保留和复合命令语义；盘点实际加载入口。
2. 同步规则与模板：一次修改同源入口，消除旧微步条款；不触碰受管分发事务的保护逻辑。
3. 建立共享验证入口：分离环境准备、构建和断言，增加可靠退出状态、命中检查及有界摘要；不按业务任务生成专用元检查器。
4. 迁移一个试点任务：保留旧记录，只提取当前阶段及未完成门禁；验证状态卡和真实证据之间的关联。
5. 对照测量：在相同任务范围和验收要求下比较交互、token与墙钟时间，再决定是否推广。

### 9.1 必需反例

| 验收场景 | 预期结果 |
|---|---|
| 同一阶段连续编辑多个文件 | 不增加计划、ADR或逐文件指纹调用；相关验证仍运行 |
| 阶段中契约被外部替换 | 不继续依据旧授权推进，进入重新接管 |
| 用户已有暂存、未暂存和未跟踪修改 | 不覆盖、不自动提交；冲突明确报告 |
| 测试从一个函数重构成多个函数，行为不变 | 不因函数数量改变阻断 |
| 测试选择为空或必需测试被跳过 | 不通过 |
| 状态卡保存成功 | 不触发验证状态卡的无限回环 |
| 状态超过行数或字节预算 | 拒绝膨胀，保留旧卡和真实证据；不删除未完成义务 |
| 复合链第一步失败 | 依赖后续步骤不执行，整体不能报成功 |
| 测试失败但日志接收程序成功 | 整体仍失败 |
| 日志保存失败或作业超时 | 分别可见，不能记为验证完成 |
| L1容器缺工具链 | 环境阻塞；不在测试中安装或联网 |
| 最后命令成功，之前必需项失败 | 阶段门禁不通过 |
| 没有显式模式名称的咨询与修复 | 按意图进入相应流程；不扩大授权 |
| 日志被截断展示 | 摘要明确标注；完整结果的失败与告警不被遗漏 |

上述资产尚未实现和执行。它们验证控制行为，而不是检查文档里是否出现特定口号。仓库配置和受控执行入口可先独立验收；平台集成另列目标版本和能力边界，不把缺失平台证据变成所有普通任务的永久阻塞。

## 10. 预期收益：公式、示例与测量边界

目前不知道全任务实际 token 节约率。Insufficient evidence. 以下为计算模型与情景估算，不是基准测试结果，不相加或相乘宣称累计收益。

### 10.1 可计算的局部收益

| 优化 | 基线与假设 | 估算 |
|---|---|---|
| 状态全文读取 | 已观察994行 → 上限80行 | 单次行数减少约92.0%；不等于token精确减少92.0%。[11] |
| 用户报告的超大状态 | 假设1400行 → 80行 | 单次行数减少约94.3%；1400行未独立核验 |
| 阶段绑定往返 | 假设原5—8次 → 正常入口/出口2次 | 该类调用减少60%—75%；不是全任务调用减少60%—75% |
| 一组可批处理步骤 | 假设3个独立工具请求 → 1个监督作业 | 该组请求减少约66.7%；内部验证仍为3步 |
| 测试工具链安装 | 原入口确有安装 → 预置环境 | 目标是L1/L2安装次数为0；初始化成本移到L0，并非消失 |

### 10.2 总 token 的情景模型

设旧任务总token为T，其中可被瘦身的状态搬运占比为f，该部分实际压缩率为r；在其他工作量不变时，总token节省近似为f乘以r。

例如：

- 若状态搬运占40%，该部分token实测压缩92%，则总token预计减少36.8%。
- 若占比只有10%，相同压缩率只能减少约9.2%的总token。
- 在占比30%—60%的假设区间内，对应27.6%—55.2%的总token节省，仅是情景范围。

行数不等于token数；token计费还可能区分缓存输入、未缓存输入和输出。因此应分别测量，不用文件行数推导账单必然降低同样比例。

### 10.3 交互轮次和墙钟时间

交互估算必须先区分工具调用数、模型轮次和用户确认次数。并行返回的多个读取请求不应重复计成多个模型往返。

示意：原来12个模型往返中有6个仅服务于重复读取、指纹登记或拆开的可合并命令，移除后为6个，减少50%。这是结构示例，不是当前会话的去重统计。

单份日志显示操作从14:04:04开始，约14:04:09.330出现包开始事件，包耗时约2.72秒，约14:04:12结束；开始到包事件之间还可能包含容器启动、安装和编译等工作，不能全部归因于包安装。[12]

### 10.4 建议采集指标

- 每阶段绑定作业数、契约全文重读数、状态读取与写入字节数。
- 模型输入、缓存输入及输出token；成功日志进入上下文的字节数。
- 模型往返、工具请求、模式切换和用户确认次数。
- L0准备、构建、断言、日志处理和清理的独立耗时。
- 必需行为覆盖、失败检出、错误通过、超时及环境重建次数。

建议先选择5个以上可比试点，保持相同需求和验收范围，分别记录冷启动与热缓存结果，报告中位数、范围和异常样本。不能通过删测试、放宽隔离或把成本移到未计量阶段得到“节约”。

## 11. 评审建议与最终裁决

建议 Antigravity 原生架构师批准以下方向，但实施另行授权：

1. 开发契约指纹限制在阶段入口与出口；受管部署及破坏性清理的事务保护不变。
2. 当前状态卡最多80行并叠加字节限制；计划、ADR不记录微步流水，旧记录只读保留。
3. 删除脆弱的声明数量和文字镜像门禁，保留安全解析、授权、边界与真实行为验证。
4. 单飞按监督作业定义，允许依赖链与管道；失败传播、分级预算和日志路径保护必须同时落地。
5. 先精简规则与验证入口，再按真实需要增加控制器能力；不新增强制模式口令或新的重型前置流程。

待评审的关键取舍是：状态卡字节与摘要预算、平台日志可恢复能力、试点任务的相关验证集合，以及契约变更与普通状态更新的清晰边界。它们不阻止本提案交付，但会影响实施细节。

最终裁决：保留“没有证据就不能通过”，废除“为了证明记录证据这件事，又不断制造新的记录与检查”。减少的是重复治理劳动，不是授权、资产保护或真实验收。
