## 一、 病理解剖：从“形式化证明陷阱”转向“动态属性背压”

### 1.1 两个核心死锁的根因复盘

| 死锁现象 | 制度/规则诱因 | 为什么它本质是“脆性形式化证明 (Verus)”陷阱 |
|---|---|---|
| **死锁 1：`ana-solo` 分析阶段死锁** | “绝对禁止使用终端、绝对禁止写代码、必须基于一手可信证据” | **不可实测的绝对真理悖论**：要求结论 100% 具备一手证据，却剥夺了一切实测工具；导致分析师要么频繁弹窗求人类帮忙跑命令，要么写出缺乏地基的纸上谈兵文档。 |
| **死锁 2：`bmad-solo` 执行阶段 90/10 效用比倒挂** | “ADR 硬门禁 + 穷举边缘用例（N次重连、300s超时、状态机异常）” | **证明维护成本打断工程吞吐率**：类似手写定理证明，人类与 AI 花费 90% 的 Token 和精力去编写、修复虚构的负向边缘测试用例，实际只写了 10% 的生产业务代码，ROI 极度低下。 |

### 1.2 对标 Geoffrey Huntley 的核心启示

正如 [adr_propertyfuzzing_antithesis.md](file:///home/ecs-user/dotfiles-bmad-solo/docs/Ralph-Wiggum-Loop/adr_propertyfuzzing_antithesis.md) 揭示的：
- **形式化证明（Verus）的溃败**：业务代码稍作重构，证明引理全部崩塌，代码演进被“维护证明”彻底拖死；
- **动态属性背压（Properties + Fuzzing）的胜利**：
  1. 不去手写 50 个穷举边缘用例，而是定义系统的**高阶不变量（Invariants，如状态单调性、守恒律、幂等性、授权边界）**；
  2. 让测试工具自动变异输入，一旦违背不变量，自动收缩（Shrinking）出最小反例并提供给开发者修复；
  3. **背压的真正硬度在于“失败关闭（Fail-Closed）”**，而不是测试用例的数量。

## 二、 V4 vs V5 `ana-solo` 深度对比：为什么 V5 显得更智能？

用户的直觉完全属实：**V5 的 `ana-solo` 在实际使用中确实显著比 V4 更智能**。我们对两者进行了系统级对比：

```
     【V4: 指令稀释与形式主义枷锁】                        【V5: 认知聚焦与行动敏捷】
  +-----------------------------------+             +----------------------------------+
  | 16.2KB 超大 Prompt (~5000 Tokens) |             | 3.8KB 精炼 Prompt (~1000 Tokens) |
  | Mary / Keshav / 仪式化角色扮演    |   ====>     | 目标-依据-反证-未知 直奔主题     |
  | 绝对禁止一切终端与代码 (导致瘫痪) |             | 推演与实测物理隔离，无盲目补证   |
  +-----------------------------------+             +----------------------------------+
```

### 核心对比维度

1. **指令密度与有效注意力 (Prompt Density & Effective Attention)**：
   - V4 的规则与技能文本长达 16.2KB，充斥着大段中英文混杂的理论套话（“Mary Strategic Persona”、“Porter Rigor”、“Minto Pyramid”、“Penta-Invariants”）。
   - 现代 LLM 的推理算力在 V4 中被大量消耗在“维持角色形式”上；而 V5 仅 3.8KB，语言高度凝练，直接释放了 80% 的前置 Attention 窗口用于深度逻辑推演。
2. **行动自由度与边界清晰度**：
   - V4 把“防越权”教条化成了“双手绑死”（连 `git status` 或看一眼 Python 版本都要向人类要授权）；
   - V5 删除了形式主义繁文缛节，强调“给出可决策结论，达到最小充分可行结论后停止发散，不固定召开角色会议，不每遍重开会话”。
3. **V4.3 的优化落地**：
   - 我们已将 V5 的**高指令密度**与**反形式主义原则**完整注入 V4，并在 [bmad-suite-v4/skills/ana-solo/SKILL.md](file:///home/ecs-user/dotfiles-bmad-solo/bmad-suite-v4/skills/ana-solo/SKILL.md) 中正式确立 **“受控沙箱探针权 (Scratchpad Probe)”**，彻底终结 Deadlock 1！

## 三、 V4 背压重构的核心方案：破除 Deadlock 2 (90/10 倒挂)

在“人-AI”值守协同的 V4 体系中，背压优化的核心是**把 90% 的测试修补开销压缩回 20% 以内，让 80% 的精力回归真实功能演进**：

```
          [ 过去的 V4 脆性背压 ]                            [ 重构后的 V4 动态属性背压 ]
  +---------------------------------------+         +---------------------------------------+
  | 手写 50 个极端边缘单测 (重连/超时/注入) |         | 3~5 条高阶核心不变量 (Invariants)     |
  | 每次代码小动，40 个边缘单测报错死锁   |  ====>  | 足迹全等单测 (Footprint-Congruent)     |
  | 强制 300 行格式化 ADR 门禁            |         | 轻量级 ADR (仅重大结构变更才建)       |
  | 90% 都在修测试，10% 业务代码          |         | 失败严格关闭 (Fail-Closed) 阻断交付   |
  +---------------------------------------+         +---------------------------------------+
```

### 3.1 核心改革措施

1. **以“高阶不变量 (Invariants)”替代“穷举边缘用例”**：
   - 不再写 50 个针对特定错误码和重试计数的 Mock 测试；
   - 转为定义状态机在任何异常下必须守恒的底层属性：
     * **属性 A（状态收敛）**：任何网络中断或命令失败，工作区暂存状态必须持久化，绝不丢弃未提交改动；
     * **属性 B（单写入者）**：任何时刻只存在一个有效的锁持有者；
     * **属性 C（退出码对齐）**：失败时进程退出码严禁为 0，错误信息必须写入诊断收据。
2. **严格执行足迹全等验证 (Footprint-Congruent Testing)**：
   - 变更了哪个函数或模块，验证就只覆盖该模块的直接足迹；严禁在日常修改中强制全量回归无关的历史复杂集成套件。
3. **ADR 门禁大幅脱水与轻量化**：
   - **Bug 修复（bugfix）与运维（ops）**：硬性禁止编写与转正 ADR；
   - **结构型（structural）与算法型（algo）**：仅在引入新组件或破坏既有不变量时才撰写简明 ADR（50 行内），重点记录“决策、被否项与验证命令”，禁止形式主义小作文。
4. **失败严格关闭 (Fail-Closed Gate)**：
   - 不搞复杂的“自动重试 N 次然后降级”；一旦核心属性断言失败或超时，立即亮红灯停止并输出反例，由“人-AI”当场针对最小反例进行修复。

## 四、 DR (Deep Recon / Defensibility Review) 反向推翻审查

对 V4 动态背压重构方案进行预先验尸（Pre-Mortem），识别潜在失效模式并给出刚性防线：

### DR-1: 放开 `_bmad-output/scratch/` 探针权限，是否会导致生产代码被污染？
- **潜在风险**：Agent 借探针之名在草稿区写脚本，悄悄通过软链或跨路径覆盖 `src/` 中的源码。
- **刚性防线**：
  1. 探针脚本只能位于 `_bmad-output/scratch/` 内；
  2. 门禁与检查器通过 `git diff --name-only` 实时校验：如果生产目录发生未经授权的变动，直接判定为违背 Invariant 3（权限越界），门禁一票否决！

### DR-2: 削减 90% 的边缘测试用例，深水区并发和边界 Bug 会不会漏网？
- **潜在风险**：以前靠几十个边缘测试保底，删减后代码质量退化。
- **事实与对冲**：
  1. **手写边缘测试的本质欺骗性**：过去手写的边缘测试大多是针对特定 Mock 逻辑的自嗨，并没有覆盖真实的深水区边界；
  2. **以“属性生成 (PBT)”对冲**：使用参数化生成（如 Python 中的 `pytest` 参数化或 `hypothesis`），用 10 行属性代码自动探索数百种随机边界，比人工手写 50 个用例的探索空间大上千倍，且维护成本下降 80%。

### DR-3: 人机值守（Human-in-the-Loop）中，人类是否会再次产生疲劳？
- **潜在风险**：如果每次探针都要人工审批，人机交互依然频繁。
- **刚性防线**：
  - **只读检查与草稿区探针彻底免审批放行**；
  - 只有当分析结束、真正产出“结晶方案”并提议“实施代码修改”时，才需要人类一次性确认授权。交互频率从每轮 5~10 次弹窗下降为每个阶段 1 次确认。
