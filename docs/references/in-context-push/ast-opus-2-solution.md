# BMAD-Solo V5 终稿方案
## 将 V4 治理能力迁移为 Cline 自动化 In-Context Push

**方案状态：** 架构终稿，可据此进入源码核验与实施设计。  
**核心目标：** 将 V4 的 `/ana-solo`、`/bmad-solo`、文档治理、计划交接和执行门禁，转化为由 `dotfiles-bmad-solo` 管理、能在 Cline 工作流中自动组装上下文的能力。

这里的“无差别转换”指 **V4 的规则语义、文档关系、授权边界和失败行为不丢失**，不是逐字复制提示词，也不是把所有文件塞进每次请求。

本方案确定了 V5 的目标架构和实施顺序，但不把尚未验证的 Cline 插件钩子、SDK/CLI 上下文注入能力、`tools` 字段行为或 Claude XML 工具解析当成既定事实。

---

## 1. 架构决策摘要

V5 由四个相互配合、职责分开的部分构成：

1. **治理源与语义映射**：保留 V4 的权威规则，将规则、文档来源、阶段输入输出及门禁要求登记为可追踪的治理契约。
2. **确定性编译与受管分发**：由 `dotfiles-bmad-solo` 把治理源转换成 Cline 等宿主可消费的规则资产，并提供校验、差异审查、备份和回滚。
3. **Cline 运行时上下文组装**：任务开始时，依据当前阶段和关联清单选择适用的治理规则、项目基线、计划和其他必要文件，注入模型可见上下文。
4. **宿主工具执行与动态门禁**：通过 Cline 实际支持的工具协议执行读取、编辑、命令等操作；根据真实执行回执推进工作流、阻断或暂停。

```text
V4 治理源与项目事实
       │
       ├─ /ana-solo：分析、证据判断、ADR 候选与 pending plan
       ├─ /bmad-solo：计划实施、Preflight、执行背压与动态门禁
       └─ 文档治理：权威来源、读取规则、产物去向与阶段依赖
       │
       ▼
dotfiles-bmad-solo 编译与受管分发
       │
       ├─ Cline 固定治理内核
       ├─ 文档关联清单与宿主协议适配器
       └─ 版本、校验、差异、备份、回滚
       │
       ▼
Cline 运行时 Context Push
       ├─ 选择当前任务阶段和权威计划
       ├─ 注入项目基线及必要文档
       ├─ 明示来源、版本、缺失项和排除项
       └─ 通过宿主工具执行，并将真实回执交回模型
       │
       ▼
Plan → 用户批准 → Act → 验证门禁 → 完成 / BLOCKED / SUSPENDED
```

## 2. V4 能力迁移范围

V5 迁移的对象不是三个互不相关的提示词，而是 V4 中已经形成的规则与文档依赖关系。

| V4 能力 | V5 目标能力 | 必须保留的语义 |
|---|---|---|
| `/ana-solo` | Plan 工作流 | 证据驱动分析、明确未知、反向审查、不得擅自转入实施 |
| ADR 与 pending plan | 计划产物与交接契约 | 区分决策记录与待执行计划；计划须有明确的审批或授权状态 |
| 文档治理 | 上下文路由清单 | 何时读取什么、什么是权威来源、文件缺失或冲突时如何处理 |
| `/bmad-solo` | Act 工作流 | 使用已获准的计划；执行范围受计划与授权限制 |
| 执行背压和动态门禁 | 状态机与门禁引擎 | 根据实际回执决定继续、阻断或暂停，不以模型自述代替证据 |
| V4 提示词规则 | 宿主适配的固定治理内核 | 保留规则责任和拒绝条件，不依赖模型自行寻找外部技能文件 |

“完整迁移”需要逐条盘点 V4 实际资产后验收。仅把某个 `SKILL.md` 拼进全局规则，不构成 V4 能力迁移完成。

## 3. 文档关系是一等架构资产

V4 中“哪些文件应放在哪里、何时读取哪个文件、哪个阶段消费哪个产物”的关联，必须从散落的口头规则显式提取出来，编译为**文档关联清单**。模型不应靠猜测来重建这些关系。

### 3.1 关联清单的职责

每条关联至少描述：

- **来源**：规则、项目基线、计划、ADR 或验证记录的逻辑身份。
- **读取条件**：任务阶段、任务类型或明确用户指令。
- **依赖关系**：进入当前阶段前必须具备的上下文。
- **产物与消费者**：当前阶段创建什么，哪个后续阶段负责读取。
- **权威性与新鲜度**：来源优先级、版本或修改时间要求。
- **缺失与冲突策略**：阻断、澄清，或在规则允许时采用明确的替代入口。
- **敏感级别**：可注入内容范围及必须排除的文件类型。

可采用 YAML、JSON 或等价的机器可读格式。以下仅为概念示意，具体字段名应在实施时定稿：

```yaml
flows:
  ana_plan:
    requires:
      - governance_core
      - project_baseline
      - task_relevant_sources
    produces:
      - adr_candidate
      - pending_plan
    missing_required_context: block_or_clarify

  bmad_execute:
    requires:
      - approved_plan
      - plan_acceptance_criteria
      - project_baseline
    produces:
      - implementation_changes
      - verification_evidence
    required_gate_failure: BLOCKED
```

### 3.2 权威入口与缺失处理

- 用户明确指定了计划或来源时，绑定该指定内容；若缺失或无效，应停止相关推进并说明原因，不静默换用其他候选。
- 未明确指定时，按 V4 的权威入口规则查找；不得擅自恢复归档计划或把历史候选当作当前有效任务。
- 对来源冲突、过期或无法读取的情形，明确记录并进入澄清或阻断状态，不将推断伪装成事实。

### 3.3 计划交接

`/ana-solo` 的输出应明确区分：

- **ADR 候选**：记录分析后形成的决策及其依据，是否接受须遵循授权流程。
- **Pending plan**：供后续审阅和批准的实施方案，不代表已经获准执行。
- **Approved plan**：具备明确批准状态、实施范围和验收条件，才可被 `/bmad-solo` 作为执行输入。

从 Plan 到 Act 的转换不能只凭模型判断“看起来已批准”。

## 4. In-Context Push 的组成与数据流

### 4.1 固定治理内核

由 `dotfiles-bmad-solo` 从 V4 权威源编译并受管分发，包含：

- Plan 与 Act 的职责和转换规则；
- 文档关联清单的读取、权威性和缺失处理规则；
- 授权边界、失败背压和证据要求；
- Cline 宿主工具协议适配说明；
- 版本、来源与生成物识别信息。

### 4.2 动态任务上下文

在当前任务开始或进入新阶段时，根据关联清单选择：

- 当前项目基线；
- 用户明确指定的来源和文件；
- 当前有效 ADR 或计划入口；
- 当前门禁需要的验收标准和相关证据；
- 支持本轮推理所必需的少量其他文档。

默认采用白名单式、最小化收集；不把凭证、密钥、无关目录和超大文件内容整体注入。大段代码或证据应通过宿主支持的读取、搜索工具按需取得。

每次注入都应可追踪，至少记录来源路径或逻辑 ID、版本或校验信息、选择理由、排除项及读取失败。不得将文件未找到时的猜测内容补成“已注入事实”。

### 4.3 注入内容的优先顺序

建议按以下顺序组装，具体覆盖规则由编译器定义并测试：

1. 宿主和当前用户的授权、工具权限及安全约束；
2. V5 固定治理内核；
3. 当前阶段的文档关联与门禁要求；
4. 项目基线和指定计划；
5. 本轮任务上下文与工具返回的实际证据。

如果不同来源冲突，必须依照明确的优先级规则解决或阻断，不能让模型自行挑选更方便的一条。

## 5. Claude XML 与 Cline 工具协议边界

V4 的治理关系应写入**治理内核与文档关联清单**；Claude XML 不应承担规则数据库、文档路由或权限系统的职责。

V5 的工具层应遵循这个原则：

- 模型需要读取、写入、运行命令或操作浏览器时，使用该版本 Cline 实际支持的宿主工具机制。
- `dotfiles-bmad-solo` 可以生成 Cline 专用的协议适配说明，但不得臆造工具名、参数或权限字段，也不得与宿主签名冲突。
- 模型输出了 XML 字符串，不代表 Cline 已解析、授权或执行。是否发生工具调用，以宿主实际工具事件和回执为准。
- 不依赖 `tools: []`、移除 `tools` 字段或免责垫片来构建架构。
- 若源码和测试证明特定 Cline 版本确实要求文本格式兼容层，才把该层作为**版本绑定的适配器**，并限定它不扩大用户授权。

因此，所谓“把关联嵌入 Claude XML 调用协议底座”，在 V5 中应实现为：**把文档关联规则作为上下文路由内核随请求推送；宿主工具协议仅负责实际读取、操作和回执。**这既保留了 V4 的治理关联，又避免把未经验证的 XML 执行假设当作底座。

## 6. `/ana-solo` 与 `/bmad-solo` 状态机

推荐将 V4 的两个阶段显式化，避免分析任务被模型自行升级为代码修改：

```text
任务进入
  → 装载固定内核与项目基线
  → 解析任务类型、指定来源和当前计划
  → Plan：分析、证据判断、反向审查
  → 输出 ADR 候选 + pending plan
  → 等待用户批准或明确下一步
  → Act：执行获准计划
  → Preflight 与阶段性验证
      ├─ 必需项通过：按门禁继续
      ├─ 必需项失败：BLOCKED
      └─ 用户明确暂停：SUSPENDED
```

### Plan 阶段

- 可以分析、读取和形成计划；
- 产出必须标记证据、未知项、依赖、风险和验收条件；
- 不把任务意图或“请看看问题”解释为写入授权；
- 不自动将 ADR 候选或 pending plan 转成已批准计划。

### Act 阶段

- 只消费明确获准的计划与范围；
- 执行前检查计划、前置条件、文件归属和用户授权；
- 必须门禁失败时阻断依赖步骤，不得通过降低断言、跳过必要验证或扩大范围放行；
- 同一根因连续失败两次时按 V4 背压规则停止盲目重试，重新评估原因和方案。

提示词可以表达这些约束，但不能证明宿主实际禁止了未授权写入。需要物理只读或强制批准时，必须验证 Cline 的权限与确认机制能否提供该控制。

## 7. 编译器与受管分发设计

### 7.1 编译器职责

编译器负责把 V4 治理源及关联清单转换成宿主适配资产，而不是自由发挥式地摘要：

1. 解析 Markdown 结构和关联清单；
2. 为规则分配稳定 ID，记录源章节与目标章节的映射；
3. 依据明确的宿主模板生成治理内核；
4. 校验必需规则、引用和阶段关系；
5. 输出差异报告、版本信息、输入来源和产物校验值；
6. 对未知结构、缺失必需规则或无法证明的语义变换报错。

AST 解析只是可靠编译的基础，不自动保证语义无损。必须再结合**逐条规则追踪、结构断言、回归用例和必要的人工审查**。

### 7.2 保真与 Token 预算

- 保真优先于 Token 数量。
- Token 预算作为软约束：超限时报告超限、受影响产物和可评审的优化选项。
- 不静默删除授权边界、失败处理、证据要求、责任分工或文档关系。
- 如果静态内核过大，优先通过阶段化注入和按需读取减少每轮上下文，而不是删除规则。
- 不以编译后 Token 数量下降作为迁移成功的证明。

### 7.3 受管分发

分发流程应支持预览、目标冲突检查、事务备份、安装对账、校验和回滚。只修改明确列入受管范围的目标；不覆盖未受管用户文件，不把分发成功等同于宿主确实加载了规则。

## 8. Cline 集成路径与未决技术门槛

用户提供的补充草案称 Cline v4.1.26 文档列出了 CLI 和 SDK。**这可以作为核验候选入口的线索，但现有文本未包含可核对的源码链接或运行回执；即使 CLI/SDK 存在，也不能据此认定它们支持请求前动态注入。**

需分别核验：

| 技术项 | 当前处理方式 | 进入生产前所需证据 |
|---|---|---|
| CLI / SDK 是否存在 | 补充草案中的候选事实 | 固定版本的官方文档或源码 |
| CLI / SDK 是否能推送上下文 | 未确认 | 官方接口、源码定位及最小可复现实测 |
| Cline 是否有稳定的请求前扩展点 | 未确认；是动态 Push 的关键门槛 | 生命周期、注入位置、调用权限和回执测试 |
| `tools` 请求字段行为 | 不作为架构前提 | Provider 源码与实际请求记录 |
| 模型名冒号后缀透传 | 不作为生产路由前提 | UI、存储、请求及网关端完整链路测试 |
| Claude XML 标签是否触发工具执行 | 不作为执行机制前提 | 解析事件和真实宿主工具回执 |
| 跨 SSE 分块和长内容解析 | 待测试 | 固定版本下的分块、截断、围栏和长文件用例 |

### 集成策略

1. 优先使用经核实、受支持的 Cline 扩展接口或 SDK/CLI 能力。
2. 若只有 CLI/SDK 能接收完整任务输入，需进一步确认这是否是受支持的上下文注入方式，以及是否保留 Cline 原有工具授权、生命周期和回执。
3. 若没有稳定的运行时注入接口，先交付治理编译与分发；**将动态上下文自动推送明确标为阻塞或待实现**，不以静态全局规则冒充。
4. 如最终只能通过维护 fork 才能实现，应将其视为独立的宿主集成决策，评估升级跟进、维护成本和兼容风险后另行批准。

## 9. 网关检索与本地工具保持正交

网关搜索不是 Context Push 的前置条件。它可以作为独立的服务端检索能力，与工作区上下文组装并行演进。

- 服务端若搜索、抓取并向模型上下文注入结果，应称为**检索增强代理**，而不是严格纯透传。
- `:academic`、`:factcheck` 暂作为候选能力路由，必须先验证 Cline 是否接受并原样传递该模型标识，以及网关对未知后缀、检索失败和来源标注的处理。
- 本地开发服务、当前 UI 和浏览器状态属于客户端本地工具能力，应由 Cline 实际支持的工具链访问。
- 网关不能将 XML 文本重写为伪造工具调用，也不能将服务端搜索结果冒充为本地浏览器执行回执。
- 服务端检索、工作区文件读取和验证结果应分别记录来源，避免证据来源混淆。

## 10. 实施阶段与退出门槛

### 阶段 0：V4 资产盘点与语义基线

盘点实际的 V4 技能、规则、项目事实文档、ADR/计划约定、执行门禁和现有分发资产；建立规则 ID 与来源映射。

**退出条件：** 每项 V4 能力都有来源、适用阶段、输入输出和失败处理；事实、推断、假设、未知分层清楚。

### 阶段 1：验证 Cline 宿主机制

固定 Cline 版本与 Provider，核验 CLI/SDK、请求组装、工具权限、扩展点和上下文注入路径。使用无敏感信息的隔离项目，保留源码定位和运行回执。

**退出条件：** 所有生产依赖都有对应证据；未确认项标记 `UNKNOWN`，不成为实现前提。

### 阶段 2：实现 V5 治理内核与关联清单

建立机器可读的文档关联、阶段状态和门禁契约；实现确定性编译、追踪矩阵及生成物校验。

**退出条件：** 关键规则无静默丢失；缺文件、引用失效、必需规则缺失会显式失败；超预算只报告，不擅自删减硬约束。

### 阶段 3：受管分发与静态治理资产

针对经核实的 Cline 目标格式实现预览、备份、安装、对账和回滚。分别处理 Cline 与 Roo 的宿主适配，避免把其规则加载和权限语义混为一谈。

**退出条件：** 可确认资产来源和版本；回滚不覆盖无关用户改动；磁盘分发结果与宿主运行时加载状态分开报告。

### 阶段 4：最小动态 In-Context Push 原型

只在阶段 1 确认稳定注入路径后实施。先支持 Plan 只读场景与白名单上下文，加入来源标记、敏感信息排除、失败可见和注入审计。

**退出条件：** 在固定 Cline 版本中证明上下文确实进入模型请求；注入内容可审计；注入失败时不能伪装成成功。

### 阶段 5：Plan → Act → 动态门禁端到端验收

验证指定计划、待批准计划、批准计划、必需项失败、连续同根因失败及暂停等流程；分别验收宿主实际工具事件和验证结果。

**退出条件：** 阶段转换有真实证据；未批准计划不能被流程标记为已获准；必需门禁失败不得登记完成或推进依赖。

## 11. 验收矩阵

| 验收领域 | 最低验收要求 |
|---|---|
| V4 语义保真 | V4 关键规则逐条映射到 V5 产物；能够从生成规则追溯到权威源 |
| 文档治理 | 具名来源、读取条件、产物和消费者可查；缺失、冲突及明确指定路径按规则处理 |
| 上下文 Push | 能区分静态规则分发和动态上下文注入；动态注入有实际请求或宿主回执 |
| 最小化与隐私 | 仅注入必要内容；敏感文件排除规则和读取失败都有记录 |
| Plan / Act | Plan 输出与 Act 授权分离；Act 只消费当前有效且获准的计划 |
| 动态门禁 | 必需失败进入阻断；暂停有明确状态；重复同根因失败触发背压 |
| Cline 工具协议 | 以宿主真实事件和工具回执验收，不以模型输出标签验收 |
| 编译与分发 | 差异可审查，生成物可校验，安装可对账，回滚可恢复 |
| 版本兼容 | 所有运行时结论绑定明确的 Cline 版本、Provider 和测试环境 |

## 12. 最终决策

1. **V5 的权威源仍是 V4 治理资产及其项目文档约定。** V5 负责显式建模、编译、适配和运行时组装，不另造一套替代治理规则。
2. **文档关联清单是 V5 的关键新资产。** 它负责将“读哪个文件、何时读取、产物由谁消费”从口头提示提升为可校验的契约。
3. **Cline 自动 In-Context Push 是运行时能力，不等同于全局规则文件分发。** 若缺少已验证的注入入口，这一能力保持阻塞，不得宣称已完成。
4. **Claude XML 不是治理底座。** 治理路由写入内核与清单；工具操作由实际宿主协议执行；未经验证的 XML 字符串不承担执行保证。
5. **`/ana-solo` 与 `/bmad-solo` 通过显式状态机衔接。** ADR 候选、pending plan、批准计划和执行证据状态分离，执行门禁依赖真实回执。
6. **先完成 V4 语义映射与 Cline 能力核验，再实现运行时自动化。** 网关检索和模型后缀作为独立能力，不阻塞治理内核与静态分发建设。

最终方案可概括为：

> **`dotfiles-bmad-solo` 将 V4 治理源编译成可追溯的 Cline 治理内核和文档关联契约；经验证的 Cline 运行时适配器在任务与阶段边界组装最小必要上下文；宿主原生工具产生真实回执；V5 状态机据此推进 Plan、批准、Act 和动态门禁。**

这使 V4 的能力与文档关系得以整体迁移，同时把静态分发、动态推送、模型协议和工具执行区分清楚，避免用未经证实的 XML、CLI/SDK 或网关行为替代宿主机制验证。
