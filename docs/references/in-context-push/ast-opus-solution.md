## 二、收敛后的架构草案

### 1. 分为治理资产与运行时注入两条能力

- **治理资产分发**：`dotfiles-bmad-solo` 将治理源文件生成宿主可加载的规则资产，提供校验、差异审查、备份与回退。生成时保留授权边界、失败处理、证据标准和硬性不变量；超出 Token 预算时报告，不静默删减。
- **运行时 Context Push**：由经过验证的 Cline 扩展接口、SDK 或 CLI 适配器负责。自动收集前必须明确数据来源、排除规则、敏感信息处理、注入时机和失败行为。
- **边界**：全局规则可以提供静态治理指令，但不能单独证明工作区文件已自动扫描并注入。若 v4.1.26 没有稳定的运行时扩展入口，动态 Context Push 暂不进入生产实现。

### 2. 本地工具调用以宿主能力为准

Cline 的读取、编辑、命令和浏览器操作应通过经确认的宿主工具协议执行。提示词可以指导模型何时使用工具，但不能替代宿主的权限控制、确认流程或执行回执。

因此，V5 暂不要求模型输出特定 Claude XML 标签，不使用“网关伪造 `tool_calls`”作为兼容方案，也不把“免责垫片”作为必需组件。若后续实验证明某个版本确需兼容提示，应限定其用途为说明协议，不得扩大用户授予的操作权限。

### 3. 服务端检索不是纯透传

若网关根据能力标识执行搜索、抓取并将结果加入模型上下文，应将其称为**检索增强代理**，而非严格纯文本透传。契约应规定检索来源、注入位置、来源标注、失败处理和隐私日志策略。

`academic` 与 `factcheck` 可保留为能力名称，但在客户端模型名传递行为验证前，不固定采用 `model:academic` 作为唯一触发协议。检索结果不得伪装成本地浏览器执行结果；访问 `localhost` 或现场 UI 仍须依赖客户端实际支持的本地工具。

## 三、最小验证门槛

以 v4.1.26 固定版本做隔离测试，并保存源码定位与实际回执：

1. **请求组装**：分别测试 OpenAI-Compatible 与其他候选 Provider；记录实际 URL、模型标识、`tools` 字段、system/messages 结构及流式响应格式。
2. **模型后缀**：测试带冒号和普通别名经过 UI 输入、持久化、请求发送、网关接收的完整链路；若链路不稳定，改用经验证的显式路由配置。
3. **工具执行**：分别观察模型文本输出、Cline 工具解析事件和本地执行结果，三者不得混为一谈。
4. **流式边界**：测试标签被拆分到不同传输块、超长写入、围栏位于标签外及 `<content>` 内、截断和错误结束等场景；以真实文件结果和宿主回执验收。
5. **自动注入**：确认 SDK/CLI 是否提供稳定的上下文传入方式、调用生命周期、授权控制和任务回执。README 证明 CLI/SDK 存在，但未证明这些具体接口。[7]

**通过标准**：每项生产依赖均有对应版本的源码依据或可复现实测；未确认的行为标记为 `UNKNOWN`，不得由提示词、网关假设或历史经验补成 `FACT`。

## 收敛后的 V5 目标架构

V5 应由两部分组成：**V4 治理语义的宿主适配包**，以及**Cline 任务开始时的上下文组装与状态推进机制**。前者保留 V4 的规则和文档关系；后者负责把适用规则、项目基线和当前计划按任务注入 Cline 上下文，并根据工具回执推进或阻断工作流。

  ├─ bmad-solo：批准计划的实施、动态门禁、执行背压

  ├─ 固定治理内核：状态机、文档治理路由、工具协议适配

## 1. 需要完整迁移的不是“提示词”，而是 V4 的工作流契约

V4 的能力可以分成三类迁移对象：

- **规则**：Plan/Act 分工、证据纪律、授权边界、失败背压等。
- **文档治理**：哪些文件是权威来源、任务开始时要读取什么、缺失时如何处理、产物应写到哪里。
- **流程关联**：`/ana-solo` 产出的 ADR 与 pending plan 如何成为 `/bmad-solo` 的输入；工程执行如何根据验证回执继续、阻断或暂停。

V5 应为这三类内容分别保留来源与用途，而不是只把它们压缩成一段“请遵循这些规则”的说明。

| V4 能力 | V5 中的对应能力 | 迁移要求 |
|---|---|---|
| `/ana-solo` Plan 分析 | Plan 工作流 | 保留分析、证据判断、反向审查与收敛结论 |
| ADR + pending plan | 计划产物契约 | 保留产物关系、权威入口选择及后续消费关系 |
| 文档治理 | 上下文路由清单 | 明确任务类型触发哪些文件读取，以及缺失或冲突时如何处理 |
| `/bmad-solo` 工程实施 | Act 工作流 | 消费获准计划，不把分析结论误作实施授权 |
| 动态门禁和执行背压 | 执行状态与门禁 | 根据实际工具和验证回执推进，失败时阻断而非只记录提醒 |

## 2. 将文件关系编译成可执行的上下文路由

V5 的核心新增物应是一个**关联清单**，把 V4 中原本分散在提示词和文档里的规则显式化。它至少需要表达：

- **来源**：哪份规则、项目基线、ADR、计划或验证结果是该事项的权威来源。
- **读取条件**：在什么任务阶段或场景下需要读取它。
- **依赖关系**：进行某项分析或实施前，必须先取得哪些上下文。
- **产物关系**：该阶段负责生成或更新什么内容。
- **消费关系**：后续哪个阶段读取和使用这些产物。
- **失败处理**：来源缺失、冲突或过期时，是阻断、澄清还是采用显式指定的文件。

清单可按如下概念表达；这是结构示意，不预设仓库中的实际文件名或路径：

```yaml
flows:
  ana_plan:
    requires:
      - governance_rules
      - project_baseline
      - applicable_source_documents
    produces:
      - adr_candidate
      - pending_plan
    on_missing_required_context: block_or_clarify

  bmad_execute:
    requires:
      - approved_plan
      - plan_acceptance_criteria
      - applicable_project_baseline
    produces:
      - implementation_changes
      - verification_evidence
    on_required_gate_failure: blocked
```

关键点是让编译产物能追溯回 V4 的权威源，而不是把关联只留在模型必须自行猜测的文字里。工作区实际文件布局、权威入口选择规则和现行 V4 约定仍须以仓库里的真实治理文档为准。

## 3. Cline 的上下文推送应分成固定内核与任务上下文

### 固定内核

固定内核适合由 `dotfiles-bmad-solo` 编译并受管分发，包含：

- V4 的工作流边界与角色职责；
- Plan、获准、Act、门禁结果之间的状态转换规则；
- 文档关联清单的读取和解析规则；
- 缺失、冲突、验证失败及连续失败时的处理约束；
- 对 Cline 原生工具协议的宿主适配说明。

### 任务上下文

任务上下文需要在当前工作区和当前任务确定后组装，至少包括适用的项目事实基线、当前权威计划入口，以及清单判定为该任务必需的其他文档。它不应默认把整个仓库都塞入每次请求；完整代码和证据应按需通过 Cline 支持的本地读取、搜索及验证工具获得。

因此，**只安装全局规则文件不等于实现了完整的自动 In-Context Push**。它可以提供固定内核，但是否能在每项任务开始前自动发现当前工作区、选取相关文档并注入请求，还取决于 Cline 实际支持的宿主机制。

## 4. Claude XML 调用协议是执行底座，不是文档关系数据库

文档治理关系应由 V5 的内核与关联清单表达；Claude XML 调用协议负责让模型调用 Cline 宿主实际提供的工具，读取或更新对应文件，并接收真实执行回执。

二者的正确关系是：

1. 上下文路由说明当前阶段应读取哪些逻辑来源、遵循什么决策规则。
2. 模型通过宿主支持的工具协议执行具体读取或写入。
3. 宿主返回真实工具结果，模型据此更新证据状态并判断门禁。
4. 没有工具回执时，不得把“计划读取”“准备写入”或“声称验证通过”算作已完成。

因此，不建议把文档治理语义挤进 XML 工具定义，或自行重定义与 Cline 工具签名冲突的参数。V5 应适配 Cline 已支持的工具协议，而不是另造一套工具 schema。Cline v4.1.26 是否会按所设想的方式解析纯文本 Claude XML、是否提供适合的注入扩展点，仍属于待源码和运行时验证事项。

## 5. V5 工作流状态机

建议将 V4 两个技能之间的关系显式化为状态机，避免分析结论直接滑入工程修改：

```text
任务进入
  → 加载固定治理内核
  → 选择当前项目基线与权威文档
  → Plan：分析、证据分层、反向审查
  → 形成 ADR / pending plan
  → 等待用户批准或指定下一步
  → Act：消费批准计划并执行
  → 执行验证与动态门禁
      ├─ 必需项通过：继续或完成
      ├─ 必需项失败：BLOCKED，不能登记完成或推进依赖
      └─ 明确暂停：SUSPENDED
```

`/ana-solo` 和 `/bmad-solo` 在 V5 中不应仅仅是两个并列的提示词入口，而应成为这条工作流中具有明确输入、输出和转换条件的阶段。对于需要强制只读的场景，还要区分“提示词要求不写入”与“宿主实际施加只读权限”；前者本身不是物理安全门禁。

## 6. Cline 自动化路径的决策边界

V5 的目标是实现 Cline 宿主级自动上下文推送，但具体做法需要以 Cline 对应版本的实际机制为依据：

- 若 Cline 提供受支持的请求上下文注入钩子，则由适配层在任务首轮调用前组装固定内核和任务上下文。
- 若没有合适的公开钩子，需要评估可维护的扩展机制、上游支持或受控 fork；不能把外部脚本生成规则文件说成已经具备动态请求注入能力。
- 如果当前只能可靠分发全局规则，则应先交付“V4 治理内核受管分发”，并将“动态工作区上下文自动推送”标为未完成能力。
- 任何 XML 工具执行、模型名后缀或请求体行为，都需在所选 Cline 版本和 Provider 上实测，不能从设计意图推导出兼容性。

## 7. 收敛后的实施顺序

1. **建立 V4 能力映射表**：逐项登记规则、文档来源、读取条件、产物、消费者和失败处理。
2. **固定 V4 语义基线**：区分权威源、生成文件、项目事实、计划与证据，避免编译时丢失职责关系。
3. **实现 V5 关联清单和内核编译**：生成 Cline 所需的固定治理内核与可追溯关联信息；暂不声称实现动态注入。
4. **验证 Cline 宿主能力**：确认首轮上下文注入、工具协议、回执回流和必要的只读或门禁能力。
5. **实现运行时上下文组装**：按工作区和当前状态加载所需内容，并对缺失、冲突和注入失败显式报错。
6. **验证语义等价**：用 V4 场景回归 V5，包括 Plan 产出、用户批准边界、Act 计划消费、动态门禁失败和暂停路径。
7. **受管分发与回滚**：在确认目标宿主路径和写入边界后，实施 Cline 全局资产的预览、备份、更新、验证和回滚。

## 本轮方案结论

V5 应定位为：**把 V4 的规则、文档治理和阶段依赖编译为 Cline 可用的治理内核与关联清单，再由经验证的宿主适配层在任务开始时自动推送适用上下文，并通过 Cline 原生工具和实际回执驱动执行门禁。**

最重要的架构边界是：文档关联不能丢在纯口头规则里；XML 工具协议不能取代这套关联模型；全局规则分发也不能冒充动态 In-Context Push。下一步应先以 V4 实际资产完成“能力—来源—读取—产物—消费者—门禁”映射，再据此验证 Cline 的运行时集成点。
