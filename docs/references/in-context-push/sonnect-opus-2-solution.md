# BMAD-Solo V5 终稿方案：Cline 自动化 In-Context Push

## 1. 方案结论

V5 的目标应定义为：**把 V4 的治理规则、文档关系和阶段契约，转换为可追溯的上下文包；再由经过验证的 Cline 宿主集成点，在任务开始时组装并推送适用内容。**

方案由三个相互独立的部分组成：

1. **治理编译与受管分发**：把 V4 的权威规则和工作流关系整理为结构化、可校验的上下文资产。
2. **运行时上下文组装**：按当前工作区、任务阶段和依赖关系，选择必要的治理模块、项目基线和计划文件。
3. **Cline 宿主适配**：在首轮模型请求前将组装结果交给 Cline。此项必须依赖经源码核验和实测的接口；不能以全局规则文件、CLI 存在或 XML 文本输出替代验证。

Cline v4.1.26 的官方版本页面说明其提供 CLI，支持交互或 headless 使用；但这只能证明 CLI 入口存在，不能证明它支持任意上下文注入、请求前钩子或所需的授权回执。[1] 因此，宿主集成点仍是本方案的首要验证门槛。

## 2. 架构决策及其状态

### 2.1 可固化的设计决策

- **语义保真优先**：迁移 V4 的规则和流程关系，不以压缩 Token 为由删去授权边界、硬门禁、失败处置、证据要求或责任归属。
- **分离静态与动态上下文**：治理内核可以预编译并受管分发；项目基线、当前任务和相关计划则须按运行时实际工作区选择。
- **按依赖加载，而非拼接全仓库**：关联清单决定哪些来源对当前阶段必需；完整证据按需读取。
- **工具执行以宿主回执为准**：模型说“已读取”“已修改”或输出类似工具的文本，不代表 Cline 实际完成了操作。
- **授权状态独立于上下文注入**：上下文插件可以传递规则和资料，但不得被视为写入、执行命令或绕过宿主确认的授权机制。
- **服务端检索与本地工具分离**：检索代理负责其服务端来源和结果；工作区、本地服务和浏览器现场操作只能由经确认的客户端能力完成。

### 2.2 保留为待验证项的假设

下列内容不进入 V5 固化不变量，直至针对目标 Cline 版本和 Provider 完成源码核验及可复现实测：

- Cline 是否提供稳定、受支持的请求前上下文注入接口。
- OpenAI-Compatible 或其他 Provider 是否必然发送 `tools` 字段，以及能否配置为不发送。
- `:academic`、`:factcheck` 等模型后缀能否通过 UI、配置、请求体和网关完整透传。
- 模型输出的 Claude XML 字符串是否会被对应版本的 Cline 解析并执行。
- SSE 分块、长内容、截断、标签外代码围栏和 `<content>` 内代码围栏的解析边界。
- CLI 或 SDK 是否提供动态上下文输入、任务生命周期钩子和可审计执行回执。

### 2.3 明确不采用的设计

- 不把“纯文本 XML 工具标签可触发本地执行”作为未验证的集成协议。
- 不由网关正则解析模型文本或伪造 `tool_calls`。
- 不把“免责垫片”当作绕过 Provider 或工具协议限制的生产依赖。
- 不把自动分类器、提示词或静态规则宣称为宿主级只读权限或强制安全门禁。
- 不以超出 Token 预算为由静默删去必需治理条款。

## 3. 目标架构

```text
V4 权威源与项目治理资产
  ├─ ana-solo：分析、证据判断、反向审查
  ├─ bmad-solo：获准计划的实施、验证和背压
  ├─ 公共治理：授权、来源、失败与阻塞规则
  └─ 项目文档：基线、权威入口、ADR、计划
                 │
                 ▼
dotfiles-bmad-solo：编译与关联清单
  ├─ 静态治理内核
  ├─ 按阶段加载的治理模块
  ├─ 来源—依赖—产物—消费者映射
  └─ 校验、差异审查、备份与回退
                 │
                 ▼
Cline 运行时适配层（接口能力须先验证）
  ├─ 识别当前工作区与任务启动事件
  ├─ 按清单选择并组装上下文
  ├─ 在首轮请求前注入，或明确报告无法注入
  └─ 接收宿主实际工具与验证回执
                 │
                 ▼
Cline / Provider / 可选检索代理
  ├─ Cline 原生支持的本地工具
  ├─ 模型请求和响应
  └─ 独立的服务端检索能力
```

“固定治理内核已安装”与“当前任务的工作区上下文已自动注入”是两个不同状态。只有运行时适配层实际取得工作区、读取必要来源并完成请求前注入，才可报告 Context Push 成功。

## 4. V4 到 V5 的治理映射模型

迁移对象不应只是提示词文本，而应覆盖四类资产：

| 迁移对象 | 应保留的信息 | V5 表达方式 |
|---|---|---|
| 规则 | 授权、Plan/Act 边界、证据纪律、失败背压 | 治理内核和阶段模块 |
| 文档治理 | 权威来源、读取条件、缺失和冲突处理 | 上下文关联清单 |
| 阶段契约 | 输入、产物、消费者和阶段转换条件 | 工作流定义 |
| 运行证据 | 实际读取、写入、命令、测试的回执 | 宿主回执引用，不复制成第二套进度账本 |

建议每项 V4 资产建立可追溯映射，至少标记：

- 来源路径及权威级别；
- 适用任务和阶段；
- 前置依赖；
- 生成或更新的产物；
- 下游消费者；
- 缺失、冲突、过期或读取失败时的处置；
- 是否属于不可删除的硬约束；
- 对应验证场景。

缺少映射的规则不得在编译时静默丢弃，应进入未映射报告并阻断发布或要求显式审查。

## 5. 关联清单与上下文包

以下仅为建议的数据结构，不代表仓库中已经存在这些文件或接口：

```yaml
bundle_version: 1
sources:
  - id: governance_core
    authority: required
    paths:
      - "<V4治理权威源>"
    injection: every_task

  - id: project_baseline
    authority: required
    paths:
      - "<当前工作区项目基线>"
    injection: task_start
    on_missing: block_or_clarify

flows:
  analysis:
    requires:
      - governance_core
      - project_baseline
      - applicable_source_documents
    may_produce:
      - adr_candidate
      - pending_plan
    on_conflict: stop_and_report

  implementation:
    requires:
      - governance_core
      - project_baseline
      - approved_plan
      - acceptance_criteria
    may_produce:
      - implementation_changes
      - verification_evidence
    on_missing_approval: do_not_implement
    on_required_gate_failure: blocked
```

上下文包应记录 `bundle_version`、来源标识、工作区标识、选入项、排除项、读取时间、来源版本或校验摘要，以及组装结果。内容和路径需遵循项目安全策略；不需要将完整文件内容写入持久日志。

## 6. 运行时组装与状态机

### 6.1 任务启动流程

1. **确定工作区**：由宿主集成取得实际工作区根目录。无法确认工作区时，不得用仓库猜测替代。
2. **加载治理内核**：加载适用于所有任务的最低必要规则，并识别当前阶段需要的专用模块。
3. **解析关联清单**：按任务类型和阶段选择必需来源，不默认读取整个仓库。
4. **读取权威资料**：至少获取适用的项目基线、明确指定的计划或权威入口；遇到缺失、冲突或过期时按清单处理。
5. **安全过滤**：排除凭证、密钥、用户明确排除项和未获准读取的内容。
6. **组装并注入**：在首轮请求前向 Cline 提交结构化上下文。若宿主没有可验证的注入能力，应报告“未完成动态注入”，不得伪装成功。
7. **记录可追溯元数据**：记录加载了哪些来源及其状态；避免建立与现有权威任务入口相冲突的进度账本。
8. **接收真实回执**：只有 Cline 实际工具结果或验证输出才能更新执行状态。

### 6.2 阶段状态

```text
START
  → CONTEXT_LOADING
      ├─ 缺少必需上下文 / 来源冲突 / 注入失败 → BLOCKED
      └─ 必需上下文就绪 → ANALYSIS 或 APPROVED_IMPLEMENTATION
  → ANALYSIS
      → PLAN_READY
      → 等待用户授权、批准或指定下一步
  → APPROVED_IMPLEMENTATION
      → EXECUTION
      → VERIFICATION
          ├─ 必需门禁通过 → DONE 或继续依赖阶段
          ├─ 必需门禁失败 → BLOCKED
          └─ 明确暂停 → SUSPENDED
```

任务意图分类只用于选择适用上下文，不能自动提升权限。用户明确要求实施时，是否可以进入实施阶段，仍须依据适用的 V4 授权和计划规则判断。对歧义、缺少批准或缺少必需证据的情况，应停止推进并说明原因。

## 7. 编译器与保真策略

### 7.1 编译原则

编译器负责结构化、校验、模块化和宿主格式适配，不负责自行决定哪些治理约束“不重要”。

建议处理流程：

1. 读取权威源和关联清单。
2. 解析 Markdown 结构，保留标题层级、列表、代码块及其边界。
3. 按明确登记的规则切分为内核、阶段模块和参考资料模块。
4. 为每个输出单元记录源文件和源章节映射。
5. 运行必需条款断言、链接检查、来源检查和格式检查。
6. 生成差异报告、来源清单、校验摘要和宿主适配产物。
7. 任一硬约束未映射、冲突未解决或必需模块无法生成时，阻断发布。

### 7.2 Token 预算处理

Token 预算是软约束，不是删除硬约束的理由。超过预算时依次采取：

1. 按阶段拆分模块，避免非必要模块进入当前请求。
2. 对大型参考材料采用明确的按需加载，而非摘要替代权威原文。
3. 检查是否重复注入了同一来源。
4. 若必需内容仍超限，报告超限并阻断或采用已批准的分阶段加载策略。

任何摘要只能作为导航，不得替代需要逐条遵守或审计的硬规则。

## 8. Cline 集成策略与验证门槛

### 8.1 集成优先级

1. **优先：受支持的宿主扩展接口**  
   若目标版本提供稳定的请求前上下文接口，构建版本锁定的适配器，并对接口行为进行契约测试。

2. **备选：经过确认的 CLI/SDK 输入路径**  
   仅当对应 CLI/SDK 的正式接口确实能传入所需上下文、控制工作区和取得可审计回执时，才将其用于该运行模式。CLI 存在本身不足以满足这些条件。[1]

3. **后备：最小受控 fork 或上游扩展点**  
   如果没有可用公开接口，评估上游贡献或最小维护补丁，暴露清晰的上下文注入契约。不得依赖脆弱的内部函数猴子补丁、网络拦截或不稳定的 UI 自动化。

4. **不满足门槛时：明确阻塞**  
   可继续开发治理编译和分发，但不得把静态规则安装宣称为动态 Context Push 已实现。

### 8.2 需要验证的宿主契约

对目标 Cline 版本和每个受支持的 Provider，验证并记录：

- 任务启动事件及首轮请求前的扩展时机；
- 上下文注入接口的输入结构、大小限制、优先级和错误行为；
- 当前工作区及任务标识的取得方式；
- 注入上下文是否会被截断、重排或覆盖；
- 本地工具能力、权限提示及实际执行回执如何呈现；
- 任务失败、取消、重试和恢复时如何避免重复或过期注入；
- 若使用 CLI/SDK，其公开参数、版本兼容性和回执格式。

### 8.3 最小测试集

- 首轮请求确实包含预期内核与必需任务上下文。
- 未选入的来源没有被意外注入。
- 缺少必需文件、工作区不可用、清单冲突时进入可见阻塞状态。
- 敏感文件、凭证和排除路径不会被注入。
- 修改或切换工作区后不会复用上一工作区的上下文。
- 长上下文或预算超限时，不静默删除硬约束。
- 文本声称执行工具但无宿主回执时，不更新为已执行。
- 工具调用、取消、失败和重试后，状态与真实回执一致。

## 9. 双轨检索协议

### 9.1 客户端本地轨

- 由 Cline 实际支持的文件、命令、浏览器或其他本地工具执行。
- 能力名称、调用形式、权限和回执都以目标版本的宿主实现为准。
- 不把模型输出的 XML 标签视为工具执行成功。
- 不让网关解释、重写或伪造本地工具调用。

### 9.2 服务端检索轨

- 可提供学术资料、权威文档或事实核验能力。
- 若代理执行检索并向模型注入结果，应称为“检索增强代理”，而非严格纯透传。
- 检索结果应包含可追溯来源、检索时间和结果边界；检索失败时显式告知模型和用户。
- 检索结果不能伪装成本地页面访问或浏览器现场观测。

### 9.3 能力路由

`academic` 与 `factcheck` 可作为路由能力名称，但模型名后缀暂不定为生产唯一协议。优先选择经验证、结构明确的路由配置；只有在客户端到网关的端到端测试证明冒号后缀稳定透传后，才启用该约定。

网关应只根据明确路由元数据选择服务端检索行为，不分析 assistant 输出中的工具文本，不改写客户端工具调用。检索注入、路由选择和普通模型推理应有分别可审计的状态。

## 10. 建议的仓库交付物

以下是建议的逻辑文件布局；具体路径应在检查现有仓库结构和治理规范后决定，不能据此推断文件已存在：

- **V4 能力映射表**：记录规则、来源、触发条件、依赖、产物、消费者和失败处置。
- **上下文关联清单**：结构化描述每个任务阶段需要的来源和模块。
- **编译器与校验器**：生成宿主适配资产，执行完整性和保真检查。
- **Cline 适配器契约**：抽象任务启动、上下文注入和回执接口；在宿主能力未验证前不实现虚假的接口。
- **生成清单与差异报告**：记录源版本、生成版本、校验结果和变更范围。
- **受管分发流程**：支持预览、备份、更新、对账与回退；不覆盖用户未授权的改动。
- **端到端测试夹具**：验证注入、来源选择、隐私排除、权限边界和失败阻塞。

## 11. 分阶段实施与验收

### 阶段 0：V4 语义盘点

完成 V4 规则、项目基线、权威计划入口及其消费关系的映射。

**验收**：每项硬约束、失败分支和阶段产物均能追溯至权威源；无未解释的丢项。

### 阶段 1：Cline 集成点验证

固定目标 Cline 版本和 Provider，检查源码并进行隔离运行测试。

**验收**：请求前上下文入口、工作区识别、工具回执和失败行为均有可复现实测或明确源码契约；否则标记 `BLOCKED`。

### 阶段 2：编译与治理资产分发

实现模块化编译、来源映射、保真校验、差异审查、备份和回退。

**验收**：生成资产可追溯到权威源；超限或缺失硬条款时不会静默发布。

### 阶段 3：动态 Context Push 原型

接入已验证的 Cline 适配点，先支持只读、白名单式的上下文组装。

**验收**：首轮请求内容可验证；上下文来源、排除项和失败状态清晰可审计。

### 阶段 4：工作流与检索端到端验收

分别测试分析、计划、批准实施、验证、阻塞和暂停路径，并独立测试客户端本地工具与服务端检索轨。

**验收**：阶段转换依赖真实用户授权和执行回执；两条检索轨不互相冒充；必需门禁失败不能登记完成。

### 阶段 5：受管发布

在具体宿主路径、权限和回滚机制均确认后，发布生成资产和适配器。

**验收**：可预览差异、保留既有用户改动、验证当前受管状态并回退到上一个已知可用版本。

## 12. 最终决策摘要

V5 的确定性基石是：**保真迁移 V4 语义，显式表达文档关联，按任务组装最小必要上下文，依赖宿主真实工具回执推进状态，并将服务端检索和客户端本地工具严格分轨。**

V5 的实现前置条件是：**找到并验证 Cline 的稳定请求前注入机制。** CLI/SDK 可以作为候选入口，但其存在不能替代对上下文注入契约的证明；若没有受支持的注入接口，应先建设治理编译与分发，并将动态 Context Push 标为阻塞，而不是用静态全局规则、XML 垫片或网关伪造能力冒充完成。

因此，建议按“先完成 V4 能力—来源—依赖映射，再验证 Cline 集成点，随后实现编译与运行时组装”的顺序推进。这样既能先固化确定性治理资产，也不会把尚未证实的 Cline、Provider 或网关行为固化成生产架构。
