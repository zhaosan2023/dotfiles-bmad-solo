设计限制：

1.3 RSIHub 生命周期：职责移植，不混版本
公开 README 将循环概括为：


select → rollout → analyze → mutate → guardrail → evaluate → absorb
而当前操作符文档展开为：


select → rollout → analyze → mutate → validate → novelty
       → canonical evaluation → gate → record → reflect
两份来源的粒度不同，不能将其混合后声称是同一个固定接口。[9][13]

本方案采用七个职责阶段：

选择：选择当前有效基线与已授权目标。
执行：生成真实行为和失败证据。
分析：定位失败机制，提出最小干预。
修改：只编辑声明的规则／脚本候选面。
约束检查：查权限、冲突、重复、坏味道和必要内容丢失。
独立评估：在冻结条件下比较基线与候选。
吸收：记录接受／拒绝结果，发布获准经验。
由于原指定资料缺失，不宣称上述是论文 Algorithm 1 的逐字复现，也不编造论文“三阶隔离”的原始名称。

1.4 本方案的三层隔离
这是工程设计，不是论文原词：

上下文隔离

Coder 不读 Reviewer 的审查准备过程。
Reviewer 不读 Coder 的聊天、辩解或总结。
Reflector 从原始证据提炼；Curator 消费结构化候选，不复制全部轨迹。
写入与进程隔离

独立工作树、进程生命周期和输出目录。
调度状态、验收配置、评估器不在 Coder 可变面。
实际强隔离需要受限工具入口及 Linux 权限边界；窗格、目录和提示词不够。
评估隔离

候选不能改评估器、预期结果、测试选择政策或自己的通过回执。
发现集与保留评估集分开。
比较必须绑定同一任务、环境和评估器身份。
安全裁决：同一 Unix 用户下开放任意 Shell，只能称协作型防误操作，不能称防恶意篡改。正式无人值守若要求硬防作弊，须另行实现并验收专用运行账号／受限执行入口，且不得向候选进程暴露控制凭据。

模块二：Watchdog 防“闷头苦干”
2.1 用客观事件判断，不读模型自报进展
每个任务尝试由可信执行包装层产生以下观测：

进程存活、退出码、心跳、工具调用开始／结束。
当前阶段、调用耗时、硬截止与累计预算。
候选内容身份、变更路径、保护文件变化。
测试收集数、必需项跳过、失败测试身份、错误指纹。
审查结论、清理结果和在途动作状态。
“我快完成了”“已取得巨大进展”不改变任何门禁。

2.2 熔断策略
以下数字是建议初值，不是已测结论：

触发条件	判定方式	动作
同类修复连续失败两次	测试身份＋错误类别＋稳定堆栈指纹一致	停止当前修复，转定向反思
重复调用无新证据	相同输入身份、命令与结果，无相关内容变化	合并重复观测，触发局部重规划
单步超时	超过该工具的已声明硬截止	取消调用，核验清理，阻塞相关任务
软时间目标超限	超过阶段规划目标，但硬预算未耗尽	告警；不能自动记失败
无验证增益	固定必需集合上失败仍重复，且没有新定位证据	提议最小探针或任务拆分
预算耗尽	到达预授权运行／请求硬预算	停止新调用，进入 BLOCKED
修改保护文件	验收器、授权、规则基线、控制状态被变更	拒绝候选，保全现场
清理未知／零测试／必需跳过	缺少任务要求的证据	不放行，不以重试掩盖
“失败数减少”只能辅助判断：不同测试集合的失败数量不可直接比较，删测也不算进展。

2.3 安全叫停顺序
不要把 tmux send-keys C-c 或 kill-pane 当唯一控制手段。

先停止派发

将任务标为 STOPPING。
撤销旧尝试的事件消费资格，禁止其释放依赖。
请求合作式取消

执行包装层停止发起新工具调用。
取消支持取消的模型／MCP 请求。
终止受管进程

对已登记的受管进程组发送 TERM。
在已批准的清理宽限结束后，必要时发送 KILL。
不使用宽泛的 pkill，不杀整个 Tmux 会话。
核验静止与现场

核对进程身份，避免 PID 复用误杀。
确认没有已知在途写入和未结束子进程。
保全工作树、差异和失败回执，再冻结候选。
重要边界：

SIGSTOP 可能留下锁和暂停的子进程，适合短暂人工诊断，不宜作为夜间默认恢复协议。
进程组控制无法保证杀死自行脱离进程组的后代；严格清理需要已验证的原生生命周期控制边界。
清理不能确认时进入 BLOCKED，不继续派发。
2.4 升维与重新派发
Reflector／Architect 只接收最小失败包：


目标与验收
当前契约和候选身份
最近两次相关失败
稳定堆栈与反例
相关定义、调用方和修复 Diff
剩余预算
允许修正范围
允许提出：

用新进程按既有契约重试。
增加一个针对明确假设的确定性探针。
在相同目标／权限／验收内拆分任务。
改变已授权任务的执行顺序。
不允许自行：

删除必需验收。
扩大写入目录、网络外发或模型预算。
将架构决策改成已接受。
将失败依赖改成成功依赖。
建议总尝试上限为三次，包含首次尝试；所有 Coder 重开、审查驳回和局部修复共享这一本预算。用完后暂停，不因换窗格重新计数。

3.3 双重接受与依赖释放
AutoSwarm 的关键是：提交不是接受，接受才释放相应依赖；贡献要求发生变化后，旧接受须重新评估。

本方案规定：


accepted(task) =
    当前贡献规格满足
    AND 必需机械检查有效
    AND 独立审查批准
    AND 候选、契约、环境身份仍适用
    AND 必需输出可消费

ready(task) =
    当前授权有效
    AND 所有必需上游输出 accepted_current
    AND 资源槽可用
    AND 无写集冲突
    AND 不处于暂停／停止
不能使用：


进程退出 0 → DONE → 启动下游
正确路径是：


READY → DISPATCHING → RUNNING → SUBMITTED
      → VERIFYING → REVIEWING → ACCEPTED
      → 释放指定依赖
异常辅助状态：


STOPPING / REPLAN_REQUIRED / BLOCKED / SUSPENDED
FAILED / CANCELLED
它们是新协议的状态设计，不声称当前引擎已支持这些枚举。

3.4 文件总线可靠性
采用单写者，而不是多个窗格竞争写 graph.json：

只有调度器写权威状态。
执行包装层写各自尝试的事件文件。
Reviewer 写审查结果；由调度器验证后应用。
模型不能直接写成功状态或伪造机械回执。
建议写入规程：

在同一文件系统写完整临时文件。
校验、刷盘，再原子替换目标。
对父目录完成必要持久化操作。
每个事件绑定运行、任务、尝试、契约和输入身份。
重复事件幂等消费；旧尝试事件拒绝。
损坏状态不按“空队列”处理，而是停止派发。
“原子替换”不是跨文件事务。先保存不可变回执，再把其引用纳入一次权威快照；孤立回执可以对账，不能反过来补造成功。

3.5 Pane A → Pane B 的自动接力
推荐“控制状态先提交，Tmux 只负责唤醒”：

A 提交冻结候选。
独立验证、审查通过。
调度器保存 A 的接受引用。
计算 B 的依赖是否真正满足。
生成 B 的任务信封并预留槽位。
向 B 的专用空闲 Shell 发送固定入口：

受控 worker-entry + 已校验的绝对信封路径
B 包装层完成领取核验后返回 ACK。
没有 ACK 就对账，不能仅凭 send-keys 成功记为运行。
传输示意：


tmux send-keys -t "$PANE_ID" -l -- "$FIXED_DISPATCH_COMMAND"
tmux send-keys -t "$PANE_ID" Enter
约束：

不把 Goal、模型输出、日志或任意命令拼入 Shell。
仅向专用空闲 Shell 发送；不向正在运行的模型 TUI 注入指令。
使用参数数组和严格引用；任务 ID 不得包含路径穿越或控制字符。
Tmux 发送成功只说明按键请求成功，不说明任务开始或完成。
3.6 Git 产物必须真的到达下游
A 和 B 有不同工作树，不会因为 A 接受就自动共享代码。

最简单的个人版默认：

串行任务：由受控整合者将 A 的已接受改动纳入整合基线；B 从该基线创建。
并行任务：从同一批准基线分叉；整合按确定顺序执行。
合并冲突：进入专用整合修复，不自动选择任一方覆盖。
多上游组合后：重新运行组合影响范围内的检查。
Git 提交／检查点和整合必须列入启动授权；否则可保存补丁候选，但不能擅自提交，更不能声称已完成自动接力。

模块四：验证剪枝与纯宿主 Worktree 规程
4.1 先测“60%”的组成
将用户报告的验证耗时拆成：

4.2 三层验证门禁
层级	默认策略	必须保留的边界
L1：静态检查	使用已安装、与项目语言匹配的检查器；必要时采用既有增量缓存	不承诺毫秒级；不能以语法检查代替类型或运行验证
L2：影响范围测试	改动符号、相关调用方、模块和既有缺陷回归	AST 未覆盖动态调用时必须扩大范围
L3：属性／模糊测试	算法、解析器、核心状态机、幂等／守恒／并发不变量按需启用	属性与生成器需审查；固定 Seed 不等于完整系统确定性
用户列出的 tsc --noEmit、pyright、cargo check 是候选命令，不代表当前 Shell／Markdown 工作区已安装或应引入这些工具。

L2 的影响分析建议：


Git 差异
  → 旧／新符号身份
  → 直接依赖与反向调用
  → 已有测试映射
  → 动态与未知边保留
  → 最小必要验证集合
需要扩大验证的情况：

公共接口、包初始化、插件注册和反射。
依赖锁文件、编译设置、测试配置。
公共状态或文件／进程生命周期。
影响图无法解释的重要调用。
未知不能映射为空集合；聚焦集合收集为零不能记成功。

4.3 E2E 不盲跑，但也不能一律禁止
普通业务局部修改：不默认跑全量 E2E。
调度器、Tmux 唤醒、进程清理和 Worktree 整合修改：必须有相应真实集成检查。
本系统本身的无人值守接力：端到端生命周期测试不可被 AST 单测替代。
因此，正确政策是“禁止盲目全量 E2E”，而不是“禁止所有 E2E”。

4.4 验证结果如何复用
通过回执至少绑定：


相关源码及必需依赖身份
测试与夹具身份
工具链／配置身份
验收政策身份
必要环境条件
状态文件更新不触发业务重测。
只改变无关展示可复用不受影响的检查。
源码、测试、配置或环境改变，重验相关证据。
不能把不同候选上的零散成功结果拼成一次完整通过。
不确定和不稳定结果不作为长期通过缓存。
4.5 Worktree 规程
建议：

从明确批准的提交基线创建工作树。
主工作区现有未提交修改不自动纳入、不重置。
依赖预备由可信流程完成，不让模型随意安装。
运行目录、端口、临时文件与可写构建输出按尝试隔离。
冻结候选后，在验证视图运行既定检查。
接受后进行获准整合，再核验组合影响。
清理前确认产物保全、进程退出和工作树内容状态。
清理失败保留路径和原因，不用强删掩盖。
缓存策略：

优先复用不可变依赖和既有可信工具链缓存。
不共享候选可修改的验证结果缓存。
可写构建目录按尝试隔离；需要共享时必须验证其内容身份与并发语义。
Worktree 提供版本和目录分离，不提供权限沙箱；共享 Git 管理数据也是需要保护的边界。

模块五：脚手架自进化与 AGENTS.md 清洗
5.1 ACE 三角色必须分权，但不必常驻
ACE 的生成、反思和整理机制支持增量更新，避免反复整篇重写造成信息坍缩；这不自动证明 Unix 级隔离。

建议权限：

角色	输入	可写输出	禁止
Generator／Coder	冻结规则＋当前任务	业务候选	改验收、改宪法、自批
Reflector	原始失败、反例、修复 Diff、验证结果	经验候选	直接发布根规则
Curator	候选经验＋规则索引＋来源	增量规则提案、去重／冲突结果	扩权、覆盖失败事实
确定性发布器	获准且评估通过的规则版本	下一任务使用的快照	中途热更新当前 Coder
物理要求：

每次角色运行是独立进程／上下文。
角色复用同一窗格可以，但不能复用污染的会话。
只有发布器获得正式规则发布权限。
规则演化与业务任务分别结算预算。
5.2 六篇论文的工程化映射
论文	核验边界	工程化解法
Paper 1：ACE	支持增量、反思与整理；不把职责图当 OS 隔离证明。	三角色分权；以带身份的增量操作替代整篇重写
Paper 2：Configuration Smells	62%／42% 是样本坏味道比例。	机器可查约束移交配置；重复、矛盾、过期规则进入清洗队列
Paper 3：Evaluating AGENTS.md	自动生成上下文未普遍提高成功率且增加成本；不支持“越短越好”的普遍定理。[4]	根文件只放承重约束与路由；对新增规则做有／无对照
Paper 4：AGIT	原文 16 类、三层，结构覆盖不等于指令质量。	四板块作为本项目轻量模板，不机械填满原文全部类别
Paper 5：AHE	用分层轨迹证据驱动可审计 Harness 修改。	负向规则必须引用可观察错误／反例；自我解释不能成为唯一依据
Paper 6：效率研究	正确编号为 2601.20404；研究报告中位耗时与输出 Token 的下降。[2]	提供核验过的精准测试入口和路由；收益在本地独立测量
研究结论并不矛盾：有用的项目指引可能改善效率，而自动生成、重复或无关指令可能增加成本。它们的任务、模型与上下文条件不同，不能合并成一个通用收益公式。[2][4]

5.3 经验候选的数据结构
每条候选至少包含：


rule_id
适用模块／触发条件
失败机制
建议动作
反例／失败回执引用
修复候选身份
验证结果引用
替代或冲突的旧规则
证据等级
没有足够新证据可以“不新增规则”，不能强制每个任务产出一句教训。

负向规则示例：

在受管子进程生命周期操作中，不以父进程退出判断清理完成；只有受管后代清理证据完整时才释放相关资源。

应附反例与适用边界，而不是扩大成“所有进程操作都必须重型隔离”。

5.4 Lint Leakage 清洗器
采用确定性初筛＋人工／独立模型审查，不让关键词正则直接删规则。

分类根规则：

机器配置可承担。
业务／安全不变量。
命令导航。
实施技能。
历史经验或重复资料。
对机器可查规则：

定位实际启用的检查器与配置。
验证该约束确实被覆盖。
完成配置迁移后再移除重复自然语言。
保留必要的“如何运行检查”导航。
对冲突／重复：

精确重复可机械去重。
语义相近只生成合并候选。
不删除否定、条件、所有权或权限限制。
不能因为“编译器理论上可查”就删除目前没有工具覆盖的约束。

5.5 12,000 字符上限如何不损失义务
将它定义为“根入口发布上限”，而不是整个必需上下文或知识库上限：

根 AGENTS.md 超过 12,000 个 Unicode 字符，发布器必须先完成主题下沉。
字符数、UTF-8 字节和 Token 分别记录，不混用。
下沉文档必须可定位，路由必须保留触发条件。
活跃任务所需的必需约束仍须完整加载。
完整闭包无法交付时阻塞发布，不截断正文或静默删义务。
这与现有“必需内容保真、软预算不删义务”的已接受决策可以并存：限制根入口大小，不限制完整知识总量。

建议根入口四板块：

Commands：经过核验的常用检查入口。
Invariants：权限、业务和生命周期承重约束。
Anti-Overdesign：禁止第二账本、无依据抽象和无限递归。
Routing：问题／路径／职责到具体文档与验证配置。
这些是项目模板，不冒称 AGIT 原文板块。

5.6 稳定前缀、缓存与回音室防线
缓存设计目标：

固定公共前缀、工具描述和规则版本。
将任务、候选和最新失败放在动态后缀。
当前尝试不热改宪法。
模型、工具或规则版本变化时重新绑定。
记录实际缓存读取／写入计量；没有计量就报告未知。
只能承诺本地快照稳定，不能承诺远端 100% 命中。

回音室防线：

反思总结不是原始证据。
同一模型认可自己的规则不是独立评估。
新规则至少经过发现案例、相关反例和保留任务检验。
没有可重复收益的候选不发布。
仅针对一个失败面做最小干预，避免同时改十条规则后无法归因。
不尝试操纵远端物理 KV Cache；新进程重置的是会话输入，不是服务端显存。

启动：
    核对明确的启动授权、计划版本、任务集合和预算
    获取本运行实例的独占调度锁
    检查角色适配器与必要验证入口

    对账进程、尝试、回执和工作树
    存在未知在途动作时停止自动恢复

循环：
    读取可信执行包装层产生的完整事件

    对每个事件：
        核对 run / task / attempt / contract / input 身份
        拒绝旧尝试、重复冲突和模型伪造的机械通过
        保全对应原始回执
        按合法状态转移应用事件

    对运行任务：
        核对硬预算、重复失败、进程与保护资产
        触发叫停时：
            提交 STOPPING
            撤销旧尝试事件资格
            请求取消并终止受管进程
            核验清理
            清理未知 → BLOCKED
            清理确认 → 冻结现场并派发定向反思

    对已提交任务：
        冻结候选与验证输入
        调用可信验证入口
        缺证据 / 超时 / 必需跳过 → 不接受
        机械通过 → 派发独立盲审

    对审查完成任务：
        核对真实审查身份与批准范围
        复核候选、契约、验证条件仍适用
        通过 → 执行获准整合并保存接受输出
        驳回 → 预算内产生新尝试，或暂停

    对就绪任务：
        核对全部必需上游输出当前有效
        核对权限、写集冲突和空闲槽
        提交 DISPATCHING 与尝试身份
        生成最小任务信封
        使用固定入口唤醒专用 Tmux Shell
        收到有效领取 ACK 才进入 RUNNING

    有状态变化：
        原子提交一份完整权威快照
        生成可选只读看板投影

    达到终止条件：
        停止新派发
        对账清理与未完成事项
        输出实际完成、失败、阻塞及证据定位
派发先记状态、再执行外部动作，是为解决：

调度器在发送按键后崩溃，重启不能判断任务是否已经开始。

解决方法是领取身份和 ACK，不是盲目再发一次。

6.5 非交互端到端测试
分三层进行，不用“假模型全绿”冒充真实无人值守验收。

第一层：纯状态机测试
封闭时钟、固定事件、假适配器：

未接受上游不能启动下游。
重复事件只生效一次。
旧尝试／旧契约回执拒绝。
测试零收集、必需跳过、审查未知均不放行。
预算耗尽不能产生第四次尝试。
图修订不能降低验收或扩大权限。
规则发布失败不覆盖旧基线。
第二层：真实宿主集成，假模型
在另获授权的临时 Git 仓库、独立 Tmux 服务和封闭夹具中：

A 由脚本假 Agent 生成一次故意失败候选。
验证入口输出真实非零结果。
调度器停止 A，假 Reflector 提交合法修正建议。
新进程生成正确候选。
独立验证／假审查协议通过。
获准整合到基线。
自动唤醒 B，B 检查实际消费到 A 的产物。
结项生成经验候选，验证旧规则未被中途热改。
必须增加故障注入：

派发状态保存后、按键发送前崩溃。
按键发送后、ACK 前崩溃。
回执保存后、权威状态更新前崩溃。
重复完成事件、损坏事件和旧 PID。
子进程不退出、端口冲突、整合冲突。
人修改相关资产、候选篡改保护文件。
下游收到旧产物。
清理结果未知。
断言对象必须是实际执行次数、候选内容、Git 整合结果和进程／资源状态，不是只检查日志含有“SUCCESS”。

第三层：真实模型小规模验收
只有前两层通过，并获得模型、费用、外发与启动授权后：

使用一个小型真实任务链。
人工断开 SSH／客户端。
