建议将 dotfiles-bmad-solo 升级为“单入口、架构驱动、可暂停评审的主动工程循环”，而不是恢复企业级 BMAD 的多 Agent 编排。/bmad-solo 继续作为唯一入口，但复杂任务必须先重建工程状态、执行架构门禁、生成可评审的 Epic → Story → Task 计划，经确认后才能编码；执行中发生边界变化或重复失败时自动回到 Architect 思考模式。这样既保留个人开发的轻量性，也能利用 Antigravity 的 Skill、Artifact Review、Diff 和测试执行能力。

Key findings

当前问题不是“缺少 Architect 模式”，而是 Architect 只作为阶段性角色存在，没有成为编码过程的持续控制面。

直接核对仓库后，关键缺口是：

SKILL.md 主要执行“分级 → 选模式 → 选 Procedure → 编码 → Review”，没有编码前架构冲突门禁。
mode-architect.md、mode-developer.md、mode-reviewer.md 过于简短，未定义架构影响分析、重审条件和证据回写。
capability-map.md 注册了 9 个 Procedure，但目录中实际只有：
architecture-decision.md
build.md
code-review.md
build.md 强依赖目标项目中的 _bmad/scripts/render_skill.py，普通非 BMAD 项目可能直接无法运行。
architecture-decision.md 和 code-review.md 也依赖未随 Solo 完整安装的脚本、配置、step files 和 customization 机制。
_bmad-output/project-context.md 含字面量 \n，而且只能表达静态项目背景，不能表达任务假设、失败和开放验证义务。
当前计划没有强制建立“需求 → 架构约束 → Epic → Story → Task → 验证证据”的追踪关系。

因此，优化重点应是：

先让 Solo 包完全自包含。
把架构从 Markdown 背景升级为运行时门禁。
为 M/L 任务强制输出并暂停评审实施计划。
用结构化状态保存事实、假设、失败和验证证据。
保留单 Agent，通过状态机切换思考模式，而不是模拟多人会议。
Confirmed facts

仓库已经有一些可以保留的基础：

/bmad-solo 单入口和渐进加载设计符合个人开发需求。
已有 S/M/L 分级。
已定义 Product、Architect、Developer、Reviewer/QA、Operator 五种思考模式。
M/L 任务已经要求 Reviewer 对抗式审查。
Completion Gate 已要求检查 Diff、运行真实验证并报告风险。
architecture-decision.md 中已有 architecture spine、架构不变量、稳定决策 ID、父级约束继承等有价值的设计。

BMAD Method 官方工作流本身强调通过多个阶段逐步构建结构化上下文，而不是直接从需求跳到实现，这个思想可以保留；但 Solo 应把阶段压缩为单 Agent 的受控状态切换，而不是复制企业角色和大量工作流。

Antigravity 已具备 Skill/Slash Command、Artifact Review、计划与 Diff 审查等能力，因此 BMAD-Solo 应输出可供 IDE 展示和审查的工程产物，而不是另造一套 IDE 或命令系统。

What remains inference

以下结论属于工程假设，尚未被该仓库的对照实验验证：

结构化架构契约会比单纯要求“记住项目架构”更稳定。
强制 M/L 计划评审能减少 Agent 闷头开发和需求遗忘。
重复失败后回到架构层，会比继续局部打补丁更有效。
独立的状态校正和架构 Review 能降低“单测通过即全部完成”的错误判断。
增加门禁会提高质量，但也会增加 token、文件数量和执行时间。

对于“该方案一定提高编码质量”，目前是 Insufficient evidence，必须通过真实任务对照验证。

此外，graphharnessloop.pdf 可检索内容更接近 Graph/Loop Engineering 的设计说明或图文材料，并不是针对 AI Coding 的软件工程对照实验。它明确支持结构化输入输出、独立验证、checkpoint、retry、budget、共享状态和高风险人工中断，但不能直接证明某个 YAML Schema 或 Epic/Story 流程必然有效。

2. 明确四种状态，避免“文档和代码混成一个真相”

Normative state：架构契约规定系统应该是什么。

Believed state：Agent 当前对任务的假设和判断。
Unknown state：尚无证据确认的部分。

当代码与架构文档冲突时，不应静默选择任何一边，而应输出：

TEXT
ARCHITECTURE_DRIFT
STALE_CONTRACT
UNAPPROVED_DEVIATION
INSUFFICIENT_EVIDENCE

4. 架构契约最小 Schema
YAML
schema_version: 1
baseline:
  git_head: ""
  last_verified_at: null

components:
  - id: domain
    responsibilities: []
    owns_data: []
    allowed_dependencies: []
    forbidden_dependencies: []

interfaces:
  - id: API-001
    producer: ""
    consumers: []
    compatibility_policy: backward-compatible

invariants:
  - id: ARCH-INV-001
    statement: "Domain must not depend on infrastructure"
    severity: block
    scope: [domain]
    verification:
      type: dependency-check
      command: null

data_ownership: []

quality_budgets:
  latency_p95_ms: null
  memory_mb: null
  throughput_rps: null

change_policy:
  requires_adr:
    - public-interface-change
    - dependency-direction-change
    - data-ownership-change
    - consistency-model-change
  requires_human_approval:
    - security-boundary-change
    - destructive-migration

规则：

每个不变量必须有 ID、范围、严重级别和验证方式。
没有自动验证方式的不变量只能标为人工 Review 项。
Agent 可以提出架构契约修改，但不能静默修改 block 级不变量。
L 级任务首次生成架构基线后必须由用户确认。

6. Architecture Preflight 门禁

M/L 任务编码前必须输出：

TEXT
Architecture verdict: PASS | WARN | BLOCK | UNKNOWN

Affected components:
Affected interfaces:
Data ownership impact:
Dependency direction impact:
Applicable invariants:
Relevant ADRs:
Assumptions:
Conflicts:
Required verification:
Required next action:

语义：

PASS：未发现冲突，可以计划或实现。
WARN：风险可接受，但必须记录缓解措施和验证义务。
BLOCK：违反硬性不变量，禁止编码。
UNKNOWN：信息不足，只能先调查、Spike 或 Benchmark。

S 级只有同时满足以下条件才能走快速路径：

仅修改一个既有组件。
不改变公共接口。
不增加跨层依赖。
不改变数据所有权。
不涉及缓存、事务、并发、安全或部署。
不改变性能关键路径。

否则自动升级为 M。

8. 执行中的 Architecture Recheck

出现以下任一事件时，Developer 必须停止并切回 Architect：

修改公共接口。
新增依赖或跨层调用。
改变数据所有权、事务、缓存、并发或一致性。
实现文件或调用路径明显超出计划。
同类假设或补丁连续失败两次。
为通过测试引入特殊分支或绕过既有 Port/Adapter。
单元测试通过，但集成义务仍持续失败。
算法复杂度、数据规模假设或 NFR 发生变化。
发现架构契约与代码不一致。

下一步不得默认继续编码，而应在以下动作中选择一个：

更新计划。
拆分 Story。
执行区分性实验。
创建 ADR。
标记架构契约陈旧。
请求用户决策。

Conflicting evidence or uncertainty
BMAD-Solo 并非完全没有架构能力；现有 architecture-decision.md 已有较好的 architecture spine 思路。更准确的问题是：它没有被连接到每次计划、编码和调试决策。
完整 Graph 不一定优于单 Loop。对个人开发的小任务使用过多节点、状态文件和审批会造成过度设计。
YAML 契约本身不能保证正确；错误基线可能把错误长期固化，因此需要 stale 检测和人工确认。
同一模型切换到 Reviewer 模式不等于真正独立审查。高风险任务应优先使用新上下文、Subagent 或确定性工具。
Antigravity 官方能力支持 Skill、Artifact Review 和 Subagent 等设计方向，
 但当前本机的具体 ~/.gemini 加载和合并语义仍应通过安装测试确认，不能只依据假设硬编码。
附件支持 Graph/Loop 的工程原则，但不提供本项目质量提升的量化证据。
Open questions

实施时建议采用以下默认政策，之后再通过配置开放：

BMAD-Solo 默认必须能脱离完整 _bmad 独立运行。
S 任务不生成持久化计划。
M/L 任务默认必须暂停计划评审。
架构基线可以自动生成，但首次生成必须标注假设。
Agent 可以自动更新软性架构说明，不能自动修改硬性不变量。
公共接口、数据所有权、安全边界和破坏性迁移必须由用户批准。
Reviewer 优先使用独立上下文；不可用时采用同模型对抗式 Review 加确定性验证。
_bmad-output 保存长期事实，brain 只保存当前会话和评审产物。

当前 Antigravity 版本对 brain/ Artifact 的实际发现和展示规则。
bs.sh 是继续支持完整 BMAD 项目作为可选后端，还是彻底移除 renderer 兼容层。

Summary

最终目标不是让 /bmad-solo 变成缩小版企业 BMAD，而是把它改造成一个受架构约束的单 Agent 工程状态机：

一个入口。
多种思考模式自动切换。
编码前必须检查架构。
M/L 任务必须先输出可评审的 Epic、Story、Task。
执行中发现边界变化或重复失败时自动重新规划。
测试和 Diff 结果必须回写为有范围的证据。
只有需求满足、架构一致、证据充分、状态准确时才允许完成。

最优先落地的不是更多角色，而是四个核心能力：自包含执行、架构契约、计划审批门禁和状态校正。
