implementation2_gemini.txt 的战略方向正确，但不建议原样落地。它已经抓住“架构基线、M/L 计划审批、执行中重审、状态对账”四个核心问题，但目前仍偏声明式：Markdown 里的“必须暂停”并不能真正阻止 Agent 编辑代码，而且主路由、状态迁移、审批凭证、安装兼容与质量评估尚未形成可验证闭环。

建议将其修订为下面的 AGSL v2 实施计划：保留 /bmad-solo 单入口和单 Agent 多思考模式，只在高风险路径增加确定性状态机、审批检查点和可选 Antigravity Hook，不把个人开发重新做成企业级多 Agent 编排。

对现有实施计划的评审
应保留的设计
/bmad-solo 继续作为唯一入口。
单 Agent 自动切换 Product、Architect、Developer、Reviewer、Operator 思考模式。
S 任务走轻量循环，M/L 才生成完整计划。
M/L 必须先生成 Epic → Story → Task，再等待用户批准。
区分规范、代码事实、Agent 信念和未知项。
公共接口、数据所有权、依赖方向等变化触发架构重审。
同类失败达到上限后停止局部打补丁。
最终完成不能只依赖 Developer 的总结，必须基于 Diff、测试和架构证据重新推导。
采用 Loop-first：只有独立验证、恢复、权限隔离确有需要时才升级为局部 Graph。这符合 graphharnessloop.pdf 的核心原则。
落地前必须修正的问题

“强制阻断”目前只是提示词

WAIT_FOR_PLAN_APPROVAL 写入 Markdown，并不能保证 Agent 不调用编辑工具。必须明确两种保障等级：

Skill-only：流程约束，属于 best-effort。
Plugin + pre-tool Hook：在写文件前执行状态检查，才接近真正的硬阻断。

Antigravity 的 Skill 本身是以 SKILL.md 为入口的知识包
；官方 Plugin 机制可以封装 Skill、Hook 和其他扩展能力
。因此应先完成 Skill 兼容版本，再把硬门禁作为可选 Plugin Adapter，而不是在第一阶段假设已经具备拦截能力。

核心路由文件没有进入修改清单

当前 SKILL.md 仍然是“分级 → 选模式 → 选 Procedure → 编码 → Review”，mode-architect.md 也只有非常简短的职责描述。实施计划必须明确修改：

SKILL.md
config/AGENTS.md
mode-architect.md
mode-developer.md
mode-reviewer.md
Completion Gate

否则新增 Procedure 不会成为主流程的不可跳过节点。

缺少正式状态迁移契约

需要定义允许的状态、迁移条件、失败状态和写代码权限，不能只画流程图。

审批缺少可验证凭证

必须记录批准的是哪一版计划，而不只是保存
approved: true
。批准后计划一旦发生实质变化，原批准应自动失效。

YAML 与“自包含”目标存在依赖冲突

Python 标准库不能解析 YAML。如果要求完全脱离 _bmad、uv、PyYAML 和网络运行，建议机器状态使用 JSON/JSONL，Markdown 作为人类评审投影。

如果坚持 YAML，则必须随包固定 YAML 解析器依赖并测试离线安装，不能只写一个假设存在 PyYAML 的 Python 脚本。

12 个“假想场景”不足以证明可执行

测试必须分为：

静态包完整性测试；
确定性状态迁移测试；
Installer 沙盒测试；
Agent 行为场景测试；
改造前后真实任务对照评估。

安装策略不应继续覆盖整个全局配置

当前 bs.sh 会使用
ln -sf
覆盖全局 GEMINI.md、AGENTS.md 和整个 skills 目录。新版默认只能安装命名空间内的 bmad-solo，不得覆盖用户已有 Skills 和 Antigravity 原生配置。

AGSL v2 目标运行模型
TEXT
/bmad-solo
  ↓
INSPECT
  读取项目规则、代码、测试、Git、已有架构资料
  ↓
CLASSIFY
  根据实际影响面确定 S / M / L
  ↓
BASELINE
  读取或建立相关架构基线
  ↓
PREFLIGHT
  PASS | WARN | BLOCK | UNKNOWN
  ↓
DECIDE_ACTION
  clarify | discover | experiment | plan | implement | escalate
  ↓
  ├─ S：短计划 → Task Loop
  │
  └─ M/L：生成 Epic → Story → Task
             ↓
        WAIT_FOR_PLAN_APPROVAL
             ↓ 用户明确批准且摘要匹配
        EXECUTING_TASK
             ↓
        VERIFY_TASK
             ↓
        发生边界变化或重复失败？
             ├─ 是 → ARCHITECTURE_RECHECK
             └─ 否 → 下一 Task
  ↓
ARCHITECTURE_POSTFLIGHT
  ↓
ADVERSARIAL_REVIEW
  ↓
FINAL_RECONCILIATION
  ↓
COMPLETE | REPLAN | BLOCKED | ESCALATED
状态迁移硬规则
当前状态	允许的下一状态	进入条件	允许修改生产代码
INSPECTING	CLASSIFIED	已读取 Git、项目规则及相关代码	否
CLASSIFIED	BASELINING	S/M/L 及理由已记录	否
BASELINING	PREFLIGHT	基线已加载或标为 provisional	否
PREFLIGHT	PLANNING	M/L 且 PASS/WARN	否
PREFLIGHT	EXECUTING	S 且 PASS	是
PREFLIGHT	EXPERIMENTING	UNKNOWN，且实验范围明确	仅实验文件
PREFLIGHT	BLOCKED	违反硬不变量	否
PLANNING	WAITING_APPROVAL	计划及摘要已生成	否
WAITING_APPROVAL	EXECUTING	用户明确批准当前摘要	是
EXECUTING	RECHECK	触发实质偏离或失败预算	否
EXECUTING	VERIFYING	当前 Task 实现完成	否
REVIEWING	RECONCILING	Review 结果及证据已保存	否
RECONCILING	COMPLETE	所有硬义务关闭	否

UNKNOWN 不允许直接实现生产方案，但可以执行受限的 Spike、Benchmark 或诊断实验。实验产物不能自动并入最终实现，必须先重新执行 Preflight。

精确的 S/M/L 分类
S 级必须同时满足
修改位于一个既有组件内；
不修改公共接口；
不新增依赖或跨层调用；
不改变数据所有权；
不涉及事务、缓存、并发、安全；
不改变部署拓扑；
不触及性能关键路径。

任一条件不满足，至少升级为 M。

M 级
多文件但仍处于一个清晰边界内；
兼容性公共接口修改；
新增内部依赖；
有多个实现方案；
需要跨组件协调，但不改变系统级安全、数据或部署边界。
L 级触发条件
安全边界或权限模型变化；
数据所有权或一致性模型变化；
破坏性数据库迁移；
部署拓扑、服务拆分或基础设施变化；
多个核心组件重构；
难以回滚的公共协议变化；
关键 NFR、并发模型或性能架构变化。

分级结果必须记录 level、reasons、risk_dimensions 和 escalation_triggers，不能只由关键词决定。

完成定义

AGSL v2 只有同时满足以下条件才算落地：

所有 Capability 映射均指向真实文件。
普通非 BMAD 项目可以离线运行核心流程。
不覆盖用户既有 Antigravity 配置。
所有状态迁移通过确定性测试。
M/L 未批准时无法合法进入 EXECUTING。
每个 Task 都有范围明确的验证证据。
计划偏离会使批准失效。
Reviewer 能从原始 Diff 和证据重新推导结论。
开放硬义务未关闭时不能声明完成。
真实任务对照评估显示架构偏差和晚期返工下降，并如实报告增加的 Token、时间与人工成本。

因此，建议不要直接执行 implementation2_gemini.txt 的六个 Epic，而是按上述七个 Commit 修订后再落地。最优先的四项仍然是：包自包含、主路由改造、可验证审批状态机、Task 级架构重审闭环；Algorithm Contract、多分支 Graph 和高级 Plugin Hook 应放在核心循环稳定之后。
