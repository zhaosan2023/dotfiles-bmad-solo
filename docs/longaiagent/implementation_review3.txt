我不建议按 implementation_gemini.txt 原样落地。它正确识别了“架构没有成为运行时控制面”、Procedure 不自包含、状态管理薄弱等问题，但遗漏了你最核心的诉求：M/L 任务必须先基于现有架构生成 Epic → Story → Task 计划，并暂停等待评审，批准后才能编码。否则即使增加 YAML、Preflight 和 Reviewer，Agent 仍可能“做完架构检查后继续闷头开发”。

建议将目标明确为：保留 /bmad-solo 单入口和单 Agent，通过状态机自动切换 Product、Architect、Developer、Reviewer、Operator 思考模式；S 任务走轻量 Loop，M/L 任务进入带架构门禁、计划审批、执行重审和证据对账的受控工程循环。

原计划必须修正的问题

缺少 Epic → Story → Task 与计划审批门禁

当前计划没有增加 implementation-plan.md Procedure 和模板，也没有 WAIT_FOR_PLAN_APPROVAL 状态。这是最大的功能缺口。

提交顺序会产生中间破损版本

第 1 阶段先让 SKILL.md 调用 Architecture Gate，第 2 阶段才创建 architecture-preflight.md 和契约，意味着第一个 Commit 合入后可能引用尚不存在的流程。

单一 engineering-state.yaml 容易变成新的万能垃圾桶

项目级架构、任务假设、测试结果、失败记录不应共用一个可覆盖文件。应改成项目级 Architecture Contract、每任务状态文件和追加式 Evidence Log。

没有 Architecture Baseline 建立流程

提供模板不等于 Agent 知道如何从代码、测试、文档和 Git 状态重建架构；也没有处理契约不存在、过期或与代码冲突的情况。

“机器可检查”表述过度

Markdown Procedure 和 YAML 本身不会强制执行。必须增加确定性校验脚本，至少检查引用完整性、状态转换、审批状态、Schema 和过期指纹。

Architecture Recheck 触发条件不完整

原计划只提到连续失败两次，遗漏公共接口、依赖方向、数据所有权、事务、缓存、并发、安全边界、部署和 NFR 变化。

没有区分四种真相状态

必须区分：

Normative：架构规定应该是什么。
Actual：代码和运行证据证明现在是什么。
Believed：Agent 当前相信什么。
Unknown：还没有证据的内容。

Antigravity 融合不足

没有设计 Artifact Review 适配层、计划批准回写、可选 Subagent Reviewer，也没有处理 ~/.gemini 现有配置的安全安装问题。

验证方案过弱

“检查路径存在 + 手工跑一个 M 任务”不能证明门禁有效。需要覆盖 S 快速路径、M/L 计划暂停、架构冲突、计划偏离、重复失败、状态过期和非 BMAD 项目运行等场景。

第三阶段优先级过早

algorithm-fit 有价值，但应在最小架构闭环和场景测试稳定后再实现。

命名不一致

AGAEL / AGAS
应统一。建议采用：

Architecture-Grounded Solo Engineering Loop，简称 AGSEL。

仓库计划不应保留本机绝对路径

删除 file:///home/veryfd/...，全部使用仓库相对路径。

TEXT
/bmad-solo
    ↓
INSPECT
读取项目规则、代码、测试、Git、稳定项目上下文
    ↓
CLASSIFY

    ↓

PASS | WARN | BLOCK | UNKNOWN

        M/L：生成 Epic → Story → Task
              ↓
        WAIT_FOR_PLAN_APPROVAL
              ↓
        按 Task 实现与验证
              ↓
        触发边界变化 → ARCHITECTURE_RECHECK
              ↓

              ↓

              ↓

这不是复制企业 BMAD 的多 Agent 团队，而是保留 BMAD“架构先于 Epics/Stories、实施前做一致性检查”的渐进上下文思想。
 BMAD 本身也允许明确的小修改直接进入 Build，因此 Solo 对 S 任务保留快速路径是合理的；对 M/L 强制暂停则是针对你当前“复杂任务闷头开发”问题制定的更严格策略。

graphharnessloop.pdf 应作为设计原则使用：一个 Loop 负责完成一个受控任务，只有存在真正独立的验证、并行检索或恢复需求时才升级为 Graph；每个循环必须有 Retry Limit、Budget、Checkpoint 和退出条件。它不是“采用该方案必然提高编码质量”的实证。

Affected interfaces:

Dependency direction impact:
Applicable invariants:
Relevant ADRs:

状态语义：

UNKNOWN：禁止 Build，先调查、Spike 或 Benchmark。

Story 3.2：Architecture Recheck

出现以下事件时立即停止 Developer 模式：

修改公共接口。
新增依赖或跨层调用。
改变数据所有权、事务、缓存、并发或一致性。
涉及安全边界或部署拓扑。
文件范围或调用路径超出批准计划。
同类假设或补丁连续失败两次。
为通过测试绕过既有 Port、Adapter 或边界。
数据规模、复杂度或 NFR 假设变化。
架构契约与实际代码冲突。

下一动作必须显式选择：

更新计划。
拆分 Story。
运行区分性实验。
创建 ADR。
标记契约过期。
请求用户决策。

Epic 5：算法契约与效果评估

此 Epic 不应阻塞最小版本发布。

Story 5.1：Algorithm Fit

仅对搜索、调度、缓存、批处理、并发、优化和性能任务触发，要求声明：

算法所属组件。
输入、输出和中间状态所有者。
时间、空间、I/O 和网络复杂度。
确定性、精确性和幂等性。
超时、失败、重试、回退与回滚。

Benchmark 可以证明什么、不能证明什么。
Story 5.2：A/B 评估

选择 10–20 个真实任务，对比原版与增强版：

未批准架构偏差数。
Review 阶段才发现的跨层问题数。
重复调试次数。
Story Reopen 次数。
NFR 回归数。
把局部结果误报为整体完成的次数。
Token 和执行时间增量。
架构门禁误报率。
人工介入次数及原因。

目前没有证据证明这些改造一定提高编码质量；结论应保持为
Insufficient evidence
，直到完成真实任务对照。
