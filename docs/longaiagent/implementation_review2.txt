Loop 与 Graph 的边界

不要把 Solo 直接改造成复杂多 Agent Graph。

S 任务：短 Loop，不创建持久计划。
M 任务：带一次计划审批 Checkpoint 的顺序 Loop。
L 任务：允许按 Epic 设置 Checkpoint，并在确有独立性时使用 Subagent 或并行验证。
高风险任务：公共接口、安全边界、数据所有权、破坏性迁移必须人工审批。
每个循环：必须有完成条件、重试上限、成本预算、失败记录和升级路径。

这符合 graphharnessloop.pdf 的可迁移原则：共享结构化状态、传递 Artifact 引用、记录路由决策、限制循环次数、Checkpoint、预算和人工中断。但该 PDF 不能证明某个 YAML Schema 或 Epic/Story 流程一定提高编码质量。

修复引用、依赖、格式和包验证。
Commit 2：Architecture Baseline and Task State
契约、任务状态、证据和 stale 检测。
Commit 3：Preflight and Plan Approval
S/M/L 分级、门禁、Epic/Story/Task 和审批暂停。
Commit 4：Build, Recheck and Reconcile
Task 微循环、重审、Reviewer 和完成门禁。
Commit 5：Antigravity Adapter and Safe Installer
原生融合、命名空间、安装和卸载。
Commit 6：Algorithm Contract and Evaluation
算法约束及真实任务对照评估。

每个 Commit 都必须独立通过包完整性测试和已有场景测试，不能出现主路由先引用下一 Commit 文件的情况。

效果评估

“该方案一定提高编码质量”目前仍是 Insufficient evidence。完成核心闭环后，应选择 10–20 个真实复杂任务，对比原版与增强版：

未批准架构偏差数。
Review 阶段才发现的跨层问题数。
重复调试次数。
Story reopen 次数。
NFR 回归数。
把局部验证误报为整体完成的次数。
计划批准后的重大偏离次数。
架构门禁误报率。
Token 与执行时间增量。
人工介入次数及原因。
